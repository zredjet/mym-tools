## 1. デザイン哲学

| 項目 | 決定 |
|------|------|
| 参考アプリ | **Linear** ([linear.app](https://linear.app/)) |
| 情報密度 | ぎっしり系 — 1 画面に 20〜30 件を一覧表示できる |
| 配色基調 | **ライトモード基準**。プロトタイプ段階でダークモード切替を Tweaks に組み込み済み (将来 Phase で正式採用予定) |
| 角丸 | shadcn 既定 (中程度、`--radius: 6px` / 大要素は `--radius-lg: 8px`) |
| タイポグラフィ密度 | 行内は余白を確保 (font-size 13-14px / line-height 1.5)、行と行の間装飾は最小限 |
| ナビゲーション | **左サイドバー固定** (幅は可変 — Tweaks で 180-320px) |
| 主操作経路 | キーボード優先 (Linear 同様 `Cmd+K` 重視) |

### 1.1 「ぎっしり系」と「余白多め」の両立解釈

両者は字面では衝突するが、Linear の実際の見た目を分解すると次の整理になる:

- **行内 (1 アイテム)**: テキストが詰まらない程度の余白 (font-size 13-14px / line-height 1.5)
- **行と行の間**: 装飾最小、border は subtle (`var(--border)` ベースの極薄ライン)
- **行の高さ**: **32px (default, Linear 寄り) / 36px (Tweaks で切替可)** → 1 画面に 20〜30 件並ぶ
- **セクション間 / カード周り**: ゆとりある padding (16-24px)

「行内は余白多め (読みやすい) / リスト全体は密 (大量表示)」というのが Linear 的な解。
本ツールもこの方向で統一する。

> プロトタイプ実装での確定値: 行高 32px (compact) / 36px (comfortable) を Tweaks で切替可能とした。デフォルトは 32px (Linear 寄り)。

### 1.2 デザイン上の優先順位 (迷ったときの判断軸)

1. **キーボード操作で完結すること** > マウス操作の見栄え
2. **情報の見つけやすさ** > 装飾の魅力
3. **一貫性** (同じ操作は同じ見た目で同じ場所) > 個別画面の最適化
4. **shadcn/ui の既定値** > カスタマイズ (やむを得ない場合のみ調整)

## 2. スタイルトークン

shadcn/ui のテーマシステムと Tailwind トークンに従う。プロトタイプではこれを CSS カスタムプロパティで実装し、Tweaks 経由で動的に変更可能にして検証した。

### 2.1 配色 (ライトモード)

| 用途 | トークン (CSS 変数) | 値 (確定) |
|------|---------------------|---------|
| 背景 (アプリ全体) | `--bg` | `#FFFFFF` |
| 背景 (サイドバー) | `--bg-sidebar` | `#FAFAFA` (zinc-50 相当) |
| 背景 (muted ホバー) | `--bg-muted` | `#F4F4F5` (zinc-100) |
| 背景 (選択行) | `--bg-accent-soft` | `oklch(...)` accent の 12% blend |
| 罫線 / 区切り線 | `--border` | `#E4E4E7` (zinc-200) |
| 罫線 (強調) | `--border-strong` | `#D4D4D8` (zinc-300) |
| 主テキスト | `--fg` | `#18181B` (zinc-900) |
| 副テキスト | `--fg-muted` | `#71717A` (zinc-500) |
| 補助テキスト | `--fg-subtle` | `#A1A1AA` (zinc-400) |
| アクセント | `--accent` | shadcn 既定 blue-600 (`oklch(0.55 0.18 255)`) |
| 危険 (削除等) | `--destructive` | `#EF4444` (red-500) |

#### 2.1.1 アクセント色

**Phase 1 は blue 固定**。要件・ADR にユーザー選択を要請する根拠がなく、`projects.accent` 等のスキーマ拡張 (D-03 永劫互換に対する負担) を避けるため、ユーザー選択 UI は **Phase 2 以降に持ち越す**。下表の green / purple / red は **Phase 2 でユーザー選択化する際の予約値**で、実装上は `--accent` を切り替えるだけで連動するよう CSS トークンの分離を維持する (ハードコードしない)。

| 名前 | OKLCH | プレビュー用近似 HEX | Phase 1 の扱い |
|------|-------|------|------|
| blue | `oklch(0.55 0.18 255)` | `~#2563EB` | **固定値 (`--accent` の唯一の実値)** |
| green | `oklch(0.55 0.18 150)` | `~#16A34A` | (予約 / Phase 2) |
| purple | `oklch(0.55 0.18 305)` | `~#9333EA` | (予約 / Phase 2) |
| red | `oklch(0.58 0.18 25)` | `~#DC2626` | (予約 / Phase 2) |

> 共通の `--bg-accent-soft` は `color-mix(in oklch, var(--accent) 10%, transparent)` で派生。`--accent` の値を 1 行差し替えるだけで選択行・チップ・focus ring・プライマリボタン背景がすべて連動する構造を Phase 1 でも維持する (= Phase 2 拡張時に書き換える箇所を最小化する)。

#### 2.1.2 状態スタイル (state)

| 状態 | 背景 | 罫線 | テキスト |
|------|-----|-----|--------|
| default | `var(--bg)` | `var(--border)` | `var(--fg)` |
| hover | `var(--bg-muted)` | `var(--border-strong)` | `var(--fg)` |
| selected (active row) | `var(--bg-accent-soft)` | (左に 2px `var(--accent)`) | `var(--accent)` |
| focus (input) | `var(--bg)` | `var(--accent)` | `var(--fg)` + `box-shadow: 0 0 0 3px var(--bg-accent-soft)` |
| disabled | `var(--bg-muted)` | `var(--border)` | `var(--fg-subtle)`, `opacity: 0.6`, `cursor: not-allowed` |
| destructive | `var(--destructive)` | `var(--destructive)` | `#FFFFFF` |

ボタン variant:
- `primary`: `bg: var(--accent)` / `color: var(--accent-fg, #fff)` / hover で +5% darken
- `secondary`: `bg: var(--bg)` / `border: var(--border)` / hover で `bg-muted`
- `ghost`: 透明背景 / hover で `bg-muted`
- `destructive`: `bg: var(--destructive)` / `color: #fff` / 確認モーダルでのみ使用

| トークン | dark 値 |

| `--bg` | `#09090B` (zinc-950) |
| `--bg-sidebar` | `#0F0F11` |
| `--bg-muted` | `#18181B` (zinc-900) |
| `--border` | `#27272A` (zinc-800) |
| `--border-strong` | `#3F3F46` (zinc-700) |
| `--fg` | `#FAFAFA` (zinc-50) |

dark への切替は `[data-theme="dark"]` セレクタで `:root` トークンを上書き。コンポーネント側は意味カラーのみ参照する規律で、コンポーネント実装に変更は不要。

| 用途 | 値 |
|------|---|
| フォント (UI) | **Inter**、フォールバック: system-ui |

## 3. レイアウト

### 3.1 アプリシェル (基本構成)

```
┌─────────────────────────────────────────────────────────────────────┐
│ Top bar (40px固定)                                                   │
│ ▼ ProjectName ▾   ⌘K Search...               🌗 ⓘ                   │
├──────────────────┬──────────────────────────────────────────────────┤
│                  │                                                  │
│ Sidebar (240px)  │ Main Area (残り全幅)                              │
│                  │                                                  │
│ - Projects       │  [ モジュール固有のコンテンツ ]                    │
│ - Modules        │                                                  │
│   (現プロジェクト  │                                                  │
│    内)           │                                                  │
└──────────────────┴──────────────────────────────────────────────────┘
```

> **v0.2 変更**: トップバー右の「⚙ Settings」アイコンは「🌗 (テーマ切替)」「ⓘ (About)」の 2 つに整理。設定ページへの導線は About / プロジェクトメニュー側に集約 (シェルから直接ボタンを置かない)。

レスポンシブ:
- デスクトップアプリのため最小幅 1024px を想定
- それ以下では「サイドバー折りたたみ」相当を Phase 2 以降で検討 (Phase 1 は対象外)

UI スケールと viewport:
- UI スケールはアプリシェル全体へ適用するが、75%〜150%のどの設定でもシェルとモーダルはネイティブウィンドウの幅・高さを超えない
- ルートの containing block は viewport 単位 (`100vw` / `100vh`) ではなく percentage (`100%`) で構成し、スケールによる二重拡大を避ける
- ウィンドウ外側のスクロールは発生させない。コンテンツが収まらない場合は Main Area、一覧、モーダル本文など、設計上スクロール可能な内側領域で扱う

### 3.2 サイドバー詳細

```
┌──────────────────────┐
│ PROJECTS         [+] │   ← セクション見出し (11px uppercase muted)
│ ▸ MyProject       27 │   ← 選択中はアクセント背景 (--bg-accent-soft)

│ ▸ Personal         6 │
│ ▸ Research        11 │
│                      │
│ MODULES          🌗  │   ← セクション右にテーマ切替アイコン
│ ▣ Prompts         27 │
│ ⚭ Links           14 │

│ # Hash               │   ← Hash は count なし (stateless)

- セクション間に 16px の空き
- 各行の高さ 32px、padding 6px 12px
- 選択中の行は `--bg-accent-soft` + `--accent` テキスト + 左 2px のアクセントバー
- `件数` は 11px / `--fg-subtle` で右寄せ

### 3.3 メインエリアのレイアウトパターン

モジュール画面は基本 2 種類 + 1:

**パターン A: 一覧 + フィルタ + 新規作成** (P-1, L-1, K-1)

**パターン B: 詳細 (リストから遷移)** (P-2, L-2)

**パターン C: 編集フォーム** (P-3, L-3, K-2) — `.form-page` を共通利用、`detail-header` をヘッダにキャンセル/保存ボタンを並べる。

> **v0.2 変更 (重要)**: 編集フォーム (P-3 / L-3) から **「プロジェクト」フィールドを削除**。理由: プロジェクトはサイドバーで明示的に選択中であり、編集フォーム内で再選択させるのは冗長 + 操作の二重化につながる。アイテムは「現在選択中のプロジェクト」に自動で所属する。プロジェクト間移動が必要な場合は、別途「移動」コンテキストアクション (将来検討) で扱う。

#### 3.3.1 リストの D&D 並び替え (パターン A 共通、PR-Y / ADR-0011)

P-1 / L-1 / K-1 の一覧はユーザーが D&D で並び替えできる。Sidebar のプロジェクト並び替え (`docs/data-model.md` §5) と同じ思想を items に適用したもの。

| 項目 | 仕様 |
|---|---|
| Drag handle | 行左端のアイコン (P-1: `≡`、L-1: link icon、K-1: swatch のドラッグ領域)。**handle 上の pointerdown のみ** drag を開始する (行クリック = 詳細遷移 / 開閉と競合させない) |
| 入力 | Pointer + Keyboard 両対応。Sidebar と同じく `@dnd-kit` の `PointerSensor` (4px activation) + `KeyboardSensor` (Tab → Space → Arrow → Space) |
| スコープ | `(project_id, module_id)` 内のみ。**プロジェクト跨ぎ / モジュール跨ぎは不可** (UI 設計でも drop zone を当該リスト内に限定) |
| 永続化パターン | **Sidebar D&D と同パターン**: `arrayMove` で local state を即時更新 → `core_reorder_items(project_id, module_id, ordered_ids)` を発火 → 失敗時は `refetch` (`refreshItems`) で巻き戻し + トースト表示。確認モーダルは出さない (即時保存) |
| ソート順 | 既定で `position ASC, updated_at DESC, id DESC` (data-model.md §6.5)。「Sort: Updated ▾」セレクタを置く場合でも本順序は手動並びを最優先する (Phase 2 で `§10 U-11` として再評価) |
| 検索結果 | 横断検索 (C-6) は `position` を見ない (検索順序が優先) — 却下根拠は `data-model.md` §6.5 検索結果での扱い |

### 3.4 トップバー

```
┌──────────────────────────────────────────────────────────────────┐
│ ▼ MyProject ▾   ⌘K Search...                       🌗   ⓘ        │
└──────────────────────────────────────────────────────────────────┘

## 4. 共通コンポーネント

shadcn/ui のコンポーネントを土台とし、本ツール固有の使い方を定義する。プロトタイプではこれを React + バニラ CSS で再現したが、Phase 1 実装では shadcn コンポーネントに置き換える。

| 名前 | 用途 | shadcn / カスタム | プロトタイプの class |
|------|-----|------------------|------|
| ListRow | 一覧 1 行 (1 行コンパクト) | カスタム | `.list-row` |
| FilterBar | フィルタ + ソート + 検索 | shadcn `Select` + `Input` | `.filter-bar` |
| Button | primary / secondary / ghost / destructive | shadcn `Button` | `.btn .btn-primary` 等 |
| Tag / Badge | タグ表示 (#lang 等) | shadcn `Badge` | `.tag` |
| Modal | 編集 / 確認 / インポート等 | shadcn `Dialog` | `.modal` |
| ConfirmModal | タイプ・トゥ・コンファーム | カスタム (Dialog ベース) | C-15 で実装済み |
| EmptyState | 空状態 (アイコン + 文言 + CTA) | カスタム | `.empty` |
| CommandPalette | ⌘K オーバーレイ | shadcn `Command` | `.cmdk` |
| MarkdownView | Markdown レンダリング | `react-markdown` 想定 | `.md` |
| VariableForm | プロンプト変数入力 | カスタム | P-2 内の `.field` 群 |
| TypeTabs | URL/Path/Memo の segmented control | カスタム | `.type-tabs` |
| FormField | label + input/select/textarea + hint | カスタム | `.field` `.field-label` `.field-input` `.field-hint` |

> **v0.2 追加**: `TypeTabs` (L-3 で URL/Path/Memo を切り替える segmented control)、`FormField` を共通コンポーネントとして明示。

確定事項 (`architecture.md §9` / `data-model.md §4` / `module-contract.md §7.3` / `decisions/0008-distribution-no-autoupdate.md §2.6` / `decisions/0011-additive-schema-migrations.md §2.5`):
- **シェルなし全画面**。サイドバー・トップバーは表示しない (=モジュールも初期化していない状態)
- 表示パターン:
  - ① `db_schema_version` 不一致 (未来版 = アプリより新しい DB を開いた、`data-model.md §14.2.3` ステップ 1)
  - ② 未来 `payload_version` 検出 (新版アプリで作った item を旧版アプリで読んだ)
  - ③ DB 物理破損 (open 失敗 / PRAGMA integrity_check 失敗)
  - ④ data.sqlite が見つからない (パス権限 / ファイル削除)
  - ⑤a **migration 失敗 (pre-migration backup 取得失敗)** — additive マイグレーション開始前のバックアップが取れず停止した場合 (`ADR-0011 §2.5`、backup ファイル **未生成**)
  - ⑤b **migration 失敗 (DDL 適用失敗)** — backup は取得成功した後、DDL 適用 tx で rollback した場合 (`ADR-0011 §2.5`、backup ファイル **生成済**)
- 上のスケルトンは **パターン①** の例。原因テキストと対処候補の並び順はパターン毎に変える:
  - ①② は「最新版に更新」を主案、③④ は「バックアップから復元」を主案
  - **⑤a (backup 取得失敗)** は「**バックアップ先パス / 容量 / 書込み権限を確認**」を主案、副次案として「ログを開いて原因を確認」「容量を空けて次回起動で再試行」を案内する。**復元動線は出さない** (取得失敗 = 当該の pre-migration backup ファイルは存在しないため)
  - **⑤b (DDL 失敗)** は「ログを開いて失敗 SQL と原因を確認」を主案、副次案として「pre-migration バックアップから復元」「次回起動で再試行」を案内する。pre-migration backup が `<backups_root>/pre-op/pre-migration-v<N>-*.sqlite` に **存在することが保証されている** (取得成功後の DDL 失敗のため) ので、復元動線を明示的に出す
  - それ以外は副次案として下に並べる
- 実装側は ⑤a / ⑤b を `AppError` の variant or `bootstrap` 層の return 値で区別し、エラー画面に正しい文言を渡すこと
- **アプリ内のアクションは [アプリを終了] のみ**。Releases / ログ / バックアップへの導線は OS 既定アプリで開くだけ (アプリプロセスは終了しない)。続行ボタン (DB を無視して起動) は置かない

- **シェルなし全画面 + 操作不可** (キーボードショートカットも `Esc` 含めて無効)
- 用途: ① バックアップ復元中 ② payload version 上昇による Eager-on-Read 強制再構築中 (C-16 から起動)
- 進捗を 4 ステップで明示し ETA を出す。失敗時は C-12 へ遷移

### 6.15 C-14 破損項目管理

```
┌──────────────────────────────────────────────────────────────────┐
│ ← 設定 / メンテナンス / 破損項目                                   │
│ Eager-on-Read で読込みに失敗したアイテム: 3 件                     │
│ ─────────────────────────────────────────────────────────────    │
│  module    id              最終エラー                  操作       │
│  ──────────────────────────────────────────────────              │

│  link      01HXZ...8EA1   JSON parse error         [⋮]            │
│  color     01HY0...7C99   hex 形式不正              [⋮]            │
│                                                                  │
│  [⋮] メニュー: payload を表示 / コピーして退避 / 項目を削除          │
│                                                                  │
│  ─────────                                                       │
│  ヒント: バックアップから復元することで一括解消できる場合があります  │
│         [ バックアップ管理を開く (C-8) ]                            │
└──────────────────────────────────────────────────────────────────┘
```

確定事項 (`data-model.md §7.6`):
- 設定 → メンテナンスから手動起動 (常時サイドバーには出さない)
- 各項目の操作: ①生 payload を表示してクリップボードへ退避 ②項目削除 (C-15 タイプ・トゥ・コンファーム — id 入力) ③C-8 バックアップへの導線
- 「項目削除」は items 行を物理削除する (`is_deleted` フラグでなく)

### 6.16 C-16 検索インデックス再構築通知

```
ヘッダバナー (⌘K オーバーレイ最上部 / アプリ起動直後の通知センター):

┌──────────────────────────────────────────────────────────────────┐
│ ⓘ 新しいデータ形式 (M-Prompt v4) を検出しました。                  │
│   検索インデックスを再構築できます (推定 12 秒)。                  │
│   実行中はアプリ操作ができません。                                │
│                                                                  │
│   対象モジュール:  • M-Prompt (27 件)  ← 表示のみ・選択不可        │
│                                                                  │
│             [ あとで ]   [ 今すぐ実行 ]                            │
└──────────────────────────────────────────────────────────────────┘
```

確定事項 (`decisions/0006-payload-versioning.md §2.4` / `decisions/0007-local-backup.md §2.2`):
- **発火条件**: 起動時に `modules.<id>.last_seen_payload_version` が現行 payload version より小さい場合 (= データ形式が更新された)
- **「今すぐ実行」**: ① pre-op バックアップを自動取得 → ② C-13 メンテナンスモードへ遷移 → ③ 全件 Eager-on-Read 強制 → ④ FTS 再構築 → ⑤ `last_seen_payload_version` を更新 → ⑥ 通常画面に戻る
- **「あとで」**: その場では何もしないが、`last_seen_payload_version` は更新せず再起動時に再表示
- 実行中も `data_revision` は **増やさない** (`decisions/0007-local-backup.md §2.2` 準拠 — リード操作扱い)
- 部分実行 (一部モジュールのみ) は Phase 1 では非対応 (将来検討)

│  Harmony              │ │    │    │    │    │    │              │

- 共通シェルは維持し、内容領域だけを Adobe Color 型の左右分割ワークスペースにする。既存ライト / ダークトークンを継承し、Adobe のブランド要素や固有アセットは使わない。

## 7. 可動パラメータ (Tweaks) — プロトタイプで検証

プロトタイプには Tweaks パネルを実装し、デザイン上のパラメータを動的に切り替えて検証した。確定値は §2 に反映済。

|----------|-----|------|

>
> **C-7 設定ページの注記 (v0.7)**: C-04 / ADR-0012 に従い、モジュールごとの enable/disable UI を提供する。無効化時の sidebar / search / routing / startup restore / export / import 契約は ADR-0012 を一次ソースとする。バックアップ (C-8) とデータ移送 (C-10/C-11) は設定ページ内のセクションとして実装する。

## 9. モジュール毎の空状態

各モジュールでアイテムが 0 件のときの表示。共通コンポーネント `EmptyState` を使用 (アイコン + タイトル + サブテキスト + 1〜2 個の CTA)。

### 9.1 P-1 (Prompts) 空状態

```
       📝
  まだプロンプトがありません

  よく使うプロンプトを保存して、
  変数差し込みで再利用できます

  [ + 新規プロンプト ]   [ サンプルから始める ]
```

- CTA①: `+ 新規プロンプト` → P-3
- CTA②: `サンプルから始める` → 5 つの組み込みサンプル (翻訳/コードレビュー/要約/メール/バグ起票) を一括追加

### 9.2 L-1 (LinkMemo) 空状態

```
       🔗
  Link / Memo を追加しましょう

  URL / ローカルパス / メモを
  プロジェクトごとに整理できます

  [ + 新規 Link/Memo ]   [ ⌘V クリップボードから貼り付け ]
```

- CTA②: クリップボードに URL がある場合のみ表示 (それ以外は非表示)。貼り付け内容を解析して type を自動推定 (URL / Path / Memo)。

### 9.3 K-1 (Colors) 空状態

```
       🎨
  パレットが空です

  ブランド色や UI トークンを
  HEX/RGB/HSL/OKLCH で管理できます

  [ + 新規 Color ]   [ 画像から抽出… ]
```

- CTA②: 画像をドロップして主要色を 5 色抽出 (Phase 1 終盤の stretch goal)。

### 9.4 H-1 (Hash) 空状態

H-1 は stateless モジュールのため空状態は無し。代わりに「入力テキスト」エリアにプレースホルダ:

```
  Hello, MyMyTools!
  — テキストを入力するか、ファイルをドロップ
```

### 9.5 C-2 アプリ全体の空状態 (プロジェクト 0 件)

(§6.4 と同じ。アプリ全体で唯一サイドバーすら空のケース。)

## 12. 付録 — プロト → shadcn コンポーネント対応表

旧 `MyMyTools Prototype.bundle.html` の class / 自前コンポーネントを shadcn/ui へ置き換える際の対応表。**実装スタック (React/Tailwind/shadcn のバージョン等) は `decisions/0002-frontend-stack.md` を一次ソースとする** — 本付録はあくまで「プロトの見た目をどう shadcn に翻訳するか」の参考。

> 共通指針: プロトの class 名 (`.list-row` `.field` `.btn-primary` 等) は **CSS 変数のためにあった暫定命名**。本実装では Tailwind ユーティリティ + shadcn variant に置き換え、独自 class は最小限 (`cn()` で合成) に留める。

### 12.1 アプリシェル

| プロト | 本実装 |
|-------|--------|
| `.app-shell` (CSS Grid) | Tailwind `grid grid-cols-[var(--sidebar-w)_1fr] grid-rows-[var(--topbar-h)_1fr]` |
| `.topbar` | カスタムコンポーネント (高さ `var(--topbar-h)`) |
| `.sidebar` | shadcn `ScrollArea` 内に Project / Module セクション |
| `.sidebar-section` | プレーン `<div>` + `text-[11px] uppercase tracking-wide text-muted-foreground` |
| `.topbar-project` | `<button>` + shadcn `DropdownMenu` トリガー |
| `.topbar-search` | `<button>` で見た目だけ。クリックで shadcn `Command` (⌘K) を開く |

### 12.2 リスト

|-------|--------|
| `.list-row` | カスタム — shadcn には該当なし、Tailwind で再現 |

| `.list-row .row-icon-svg` | `lucide-react` の対応アイコン (§12.9) |

> **留保**: shadcn の `Form` / `FormField` / `FormDescription` / `FormMessage` は **react-hook-form** に依存する API ファミリーで、フォーム検証ライブラリの採用は ADR-0002 では未決定。react-hook-form を入れない判断であれば、`Form` ファミリーは使わず `Label` + `Input` + 手動エラー表示の組合せに置き換える。本表は「shadcn の Form を使う場合の最大対応」として参照する。
