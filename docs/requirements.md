# 要件定義 (Requirements)

最終更新: 2026-08-25 / ステータス: Draft (Phase 1)

このドキュメントは「何を作るか / 作らないか」「なぜそう決めたか」を残すためのものです。
実装方法 (どう作るか) は `architecture.md` 以降に分離します。

---

## 1. プロダクト概要

軽量なクロスプラットフォーム多目的GUIツール。
プロンプト管理・リンク管理・カラー選択・ハッシュ計算・配色作成といった、
日常の小さな作業を1つのアプリ内で扱えるようにする。

機能は固定セットではなく、**モジュールとして後から追加できる**ことを前提とする。
ユーザー個人が手元で使うローカルツールであり、サーバーや共有を前提としない。

### 1.1 想定ユーザー
- 開発者・クリエイター個人
- 「ちょっとした作業のためにブラウザのタブを開く / 専用アプリを起動する」
  という小さな摩擦を1か所に集約したい人
- データはローカルに置きたい / クラウド同期は必須としない人

### 1.2 解決する課題
- プロンプト・リンク・カラーコード等を**ばらばらのツール / メモアプリ**で管理している
- 同じハッシュ計算やカラー変換を都度Webツールで済ませている
- 既存のオールインワンツールは**重い / 起動が遅い / 自分の使う機能と合っていない**

### 1.3 設計の中心思想 (なぜこの設計か)
1. **軽量性が最優先** — Electron的な重さを避けるために Tauri v2 を採用
2. **項目はプロジェクトに属する** — フラットなリスト管理だと項目が増えたとき破綻するため、
   プロジェクトを第一級概念にする
3. **モジュール独立** — 機能追加でコアを書き換えない構造にすることで、
   個人ツールでありがちな「機能が増えた結果メンテ不能になる」状態を防ぐ
4. **データは壊さない** — アプリ更新で「過去のプロンプトが開けません」を絶対に起こさない

## 2. 機能要件

### 2.1 コア機能 (アプリ本体が提供する)

| ID | 要件 | 備考 |
|----|------|------|
| C-01 | プロジェクトの作成・名前変更・削除ができる | プロジェクトは項目の所属単位 |
| C-02 | プロジェクト内検索とプロジェクト横断検索の両方ができる | 既定はプロジェクト内、UIから横断に切り替え可能 |
| C-03 | アプリ全体の設定 (テーマ / 既定プロジェクト等) を保存・復元できる | |
| C-04 | モジュールの一覧表示・有効/無効の切り替えができる | 無効化したモジュールはサイドバー等から消える |
| C-05 | アプリ起動時、前回の状態 (開いていたプロジェクト・モジュール) を復元できる | |
| C-06 | データのエクスポート / インポートができる | 単位は「アプリ全体」と「プロジェクト単位」の両方をサポート。形式は JSON |

### 2.2 搭載モジュール

#### M-Prompt: プロンプト管理
- プロンプト本文をプロジェクトに紐づけて保存できる
- タイトル・タグ・更新日時を持つ
- 全文検索ができる (プロジェクト内 / 横断の両方)
- プロンプト本文を **Markdown としてレンダリング表示** できる(コードブロック内のシンタックスハイライト含む)
- 変数プレースホルダ (例: `{{topic}}`) を本文に埋め込める
  - プロンプトを開くと、検出された変数ごとに入力欄が表示される
  - 入力値を差し込んだ後の**完成プロンプト**をプレビュー表示し、ワンクリックでクリップボードにコピーできる
  - 変数を持たないプロンプトは、本文をそのままワンクリックコピーできる

#### M-Link: リンク管理 (`id = linkmemo`)
公開済みIDを維持し、以下の2種を扱う。タイトル・タグ・任意メモ・更新日時を共通フィールドとする。
- **URL**: ワンクリックで既定ブラウザで開く
- **ローカルファイルパス / ネットワーク (NAS等) ファイルパス**: ワンクリックで OS 既定のファイラー (Explorer / Finder) で該当フォルダ・ファイルを開く
- ファビコン取得など外部リソースへのアクセスは**任意**(オフライン動作を阻害しない範囲で)

#### M-Memo: 単独メモ管理 (`id = memo`)
- Markdown本文、タイトル、タグ、更新日時を持ち、全文検索できる
- 一覧、詳細、作成、編集をモーダルではなくモジュール内ページで提供する
- 詳細はMarkdown / Raw切替、本文コピー、編集動線を持つ
- 作成・編集は大きな本文欄と明示的な保存 / キャンセルを持ち、未保存遷移を確認する

#### M-Color: カラー選択
- HEX / RGB / HSL の相互変換ができる
- 任意のカラーを単色アイテムとしてプロジェクトに保存できる
- スポイト (画面上の色を拾う) は**初期版では対象外**(OS API依存が大きいため後送り)

#### M-Hash: ハッシュ計算
- テキスト入力に対して MD5 / SHA-1 / SHA-256 / SHA-512 を計算する
- ファイルドラッグ&ドロップでのファイルハッシュ計算に対応
- 計算は完全ローカル

#### M-Palette: カラーパレット作成
- M-Color とは独立したモジュールとして、5 色固定のカラーパレットを作成・保存できる
- 色相環と Custom / Analogous / Complementary / Split complementary / Triad / Square / Compound / Shades / Monochromatic の 9 種の調和ルールを提供する
- 各色のロック、並び替え、HEX/RGB/HSL/OKLCH 編集、ランダム生成、Undo/Redo、HEX コピーに対応する
- パレットはプロジェクト単位で保存し、名前・タグ・5 色の順序・調和ルール・基準色位置を保持する
- 初期版では画像抽出、コントラスト確認、色覚シミュレーション、共有、ダウンロード、スポイト、M-Color との自動同期を対象外とする

#### 開発ツール拡張 (ADR-0014 / ADR-0015)

小さな機能を統合せず、一機能一モジュールの単位で次の stateless モジュールを搭載する。いずれも入力・結果・履歴・プリセットを永続化せず、items、検索、export / import の対象外とする。

| モジュール ID | 機能 | 主な範囲 |
|---|---|---|
| `regex` | 正規表現プレイグラウンド | ECMAScript RegExp、match / capture / replace preview |
| `textdiff` | テキスト差分ビューア | 行・単語差分、空白・大文字小文字の無視 |
| `codec` | エンコード／デコード変換 | Base64 / Base64URL / URL percent / HTML entity / Unicode escape |
| `jwt` | JWTインスペクター | decode、`exp` / `nbf` / `iat` 表示。署名検証・生成は行わない |
| `urlquery` | URL・クエリパラメータ編集 | URL分解、重複・順序を保つquery編集 |
| `datetime` | 日時・Unix Timestamp変換 | Unix秒・ミリ秒、ISO 8601、IANA timezone |
| `idgen` | UUID／ULID／ランダムID生成 | UUID v4 / v7、ULID、NanoID |
| `secretgen` | 安全なランダム文字列生成 | 暗号学的乱数によるpassword、Hex / Base64URL token |
| `cron` | Cron式ビルダー | Unix 5 field / 秒付き6 field、次回実行日時 |
| `http` | HTTPリクエスト実験ツール | Rust IPC経由の軽量REST client。既定無効 |
| `a11y` | Webアクセシビリティ確認 | WCAG 2.2 contrast、色覚シミュレーション |

### 2.3 拡張性に関する要件

| ID | 要件 |
|----|------|
| E-01 | 新しいモジュールをコア改修なしで追加できる構造であること |
| E-02 | モジュールは独自のUIと独自のデータスキーマを持てること |
| E-03 | モジュールは「コアが提供するAPI」経由でのみストレージや設定にアクセスすること(モジュール間の直接依存を禁止) |
| E-04 | モジュールが将来増減してもデータベースのマイグレーションが**コア起因では発生しない**こと |

## 3. 非機能要件

### 3.1 パフォーマンス / 軽量性
- **起動時間**: コールドスタートで 1.5 秒以内 (中位スペックPC)
- **メモリ常駐**: 起動直後 100MB 以下を目標 (Tauri は OS 標準 WebView を借りるため Electron 比で削れる。ただし WebView ベースラインの制約で 80MB 未満は困難)
- **インストーラサイズ**: 30MB 以下を目標 (Tauri採用の主な動機)
- 数千件規模のプロンプト/リンクで操作が体感的にもたつかないこと

> これらは厳格な合否ラインではなく**設計判断の指針**。
> 数値が達成できないときは「なぜ達成できないか」を decisions/ に残す。

### 3.2 互換性
- Windows 10 / 11 (x64) 対応
- macOS 12 以降 (Apple Silicon / Intel) 対応
- Linux は**サポート対象外**。Phase 1 では検証もテストも行わない(将来追加が必要になった場合でも、単純な拡張範囲で済む構造を維持する)

### 3.3 データ永続性 / 互換性
- アプリのバージョンアップにより、既存ユーザーデータの**手動マイグレーション作業を発生させない**
- モジュール固有のフィールド変更は JSON カラムで吸収する (詳細は `data-model.md`)
- データベースファイルは平文 SQLite (個人ローカルツールのため暗号化は必須要件としない)

### 3.4 オフライン動作
- ネットワーク接続なしで全主要機能が動作すること
- 外部サービスへの問い合わせ(ファビコン取得等)は**任意機能**として明示的にON/OFFできる
- `http` モジュールは明示的な通信実験用の例外として既定無効にし、利用者が設定画面で有効化する

### 3.5 国際化
- UI言語は**日本語のみ**(Phase 1)
- 多言語化を見越した文字列外出し等の準備は**行わない**(個人用ツールのため YAGNI)
- ユーザーデータ自体は当然 Unicode で保存される

### 3.6 アクセシビリティ
- キーボードのみで主要操作 (プロジェクト切替・項目追加・コピー) ができること
- shadcn/ui + Radix Primitives がベースなので、コンポーネントレベルのa11yは標準準拠

### 3.7 セキュリティ
- ローカル個人ツールであり、認証・権限管理はスコープ外
- ただし「クリップボード経由でプロンプト本文が他アプリに漏れる」など
  ユーザーの明示操作を伴う情報露出は仕様として許容

### 3.8 配布 / 更新
- コード署名は**実施を前提とする**(macOS Gatekeeper / Windows SmartScreen 対策)
- **自動更新は実装しない**
- ユーザーが新バージョンのアプリ実行ファイル / フォルダを **エクスプローラー (Finder) 上で差し替えるだけで更新が完結する** 配布構成にすること
  - macOS / Windowsともにportable ZIPを配布し、インストーラは生成しない (ADR-0013)
  - macOS ZIPにはApple Silicon向け`.app`、Windows ZIPにはx64 `.exe`を格納する
  - ユーザーデータ (SQLite ファイル等) はアプリ実行ファイルと**同じディレクトリに置かない**(差し替え時に消えないように、OS 標準のユーザーデータディレクトリへ配置する)

## 4. やらないこと (Out of Scope)

スコープを締めるための明示的な非対象。
「やる」と判断するときは要件定義の改訂で明示する。

### 4.1 Phase 1 では作らない
- **クラウド同期 / 複数端末間のリアルタイム同期**
  - 理由: ローカルファースト思想。同期は別レイヤとして将来検討
- **複数ユーザー / アカウント / 認証**
  - 理由: 個人ローカルツールである
- **共同編集・共有リンク**
  - 理由: 同上
- **AI推論機能 (プロンプトを実際に実行する等)**
  - 理由: プロンプト「管理」ツールであり、実行は外部ツールに委ねる
- **モバイル (iOS / Android) 対応**
- **Linux サポート**
- **プラグインの動的ダウンロード / マーケットプレイス**
  - 理由: モジュールは当面ビルド時組み込み (詳細は architecture.md で確定)
- **ファイル全般のメモ・添付管理**
  - 理由: ハッシュ計算でのファイル参照を除き、ファイル管理ツールにはしない

### 4.2 永続的にやらない (現時点の判断)
- **エンタープライズ向け機能** (監査ログ / 組織管理 / SSO)
  - 個人ツールとしての軽量性を損なう

## 5. 決定事項 (Phase 1)

要件定義段階で確定した設計判断。詳細は `architecture.md` / `data-model.md` / ADR に展開する。

| ID | 決定 | 理由 / 制約 |
|----|------|-----------|
| D-01 | 「プロジェクト」は全モジュールに適用する | 設計の割り切り。モジュールごとにスコープ概念を分岐させない。ステートレス系 (Hash) でも UI 上はプロジェクト配下に置かれる |
| D-02 | モジュールはビルド時組み込み (静的) | 個人用ツールでありプラグインマーケット等は不要。機能追加・差し替えはアプリのリリース単位で行う |
| D-03 | データ移行不要を**原則として永劫**で守る | やむを得ない場合のみ移行を許可し、その例外は ADR に必ず記録する。詳細仕様は `data-model.md` |
| D-04 | 自動更新は実装しない | ユーザーがエクスプローラー / Finder でアプリを差し替えるだけで完結する配布構成にする (3.8 参照) |
| D-05 | エクスポート/インポートは「アプリ全体」と「プロジェクト単位」の両方を提供 | C-06 に反映済み |
| D-06 | Hash モジュールは items テーブルに何も保存しない (旧 Q-06) | プロジェクトは UI 上の所属としてのみ扱う。後から履歴を残す方針に変えても items に書き始めるだけで済む(後方互換) |
| D-07 | エクスポート/インポートは単一 JSON ファイル。ルートに `schema_version` を持つ (旧 Q-07) | バイナリ添付がなく、diff/Git 親和性が高い。将来添付機能を入れる場合に ZIP 化を再検討 |
| D-08 | ADR-0016によりM-LinkとM-Memoへ分離する。M-Linkは `url` / `path` を扱い、ローカルとネットワークパスは `type=path` に統合、`file://` はパスへ正規化する。単独MemoはM-Memoで扱う | 大量登録時の判別性と長文編集の可読性を優先する。公開済みID `linkmemo` はLinkとして維持し互換性を守る |
| D-09 | Markdown は `react-markdown` + `remark-gfm` で描画し、raw HTML はレンダリングしない。コードブロックのシンタックスハイライトは **rehype-highlight** (highlight.js ベース) を採用 (旧 Q-09 / Q-16 解決) | サニタイズはライブラリ既定の挙動で十分。ローカルツールでも自衛として raw HTML を許可しない。バンドル軽量・CSS テーマ切替で完結する点で Shiki より Phase 1 方針に整合する |
| D-10 | Rust 側の SQLite ライブラリは `rusqlite` を採用 (旧 Q-10) | コンパイル時クエリ検証より起動時依存の薄さを優先。設計思想 (軽量性 / シンプル) と整合 |
| D-11 | items テーブルの全行に `payload_schema_version` を持たせ、**Eager-on-Read** 方式で payload のスキーマ進化を吸収する。古い行を読んだ時点で payload と search_text を現行版に再生成し、items を UPDATE する。起動時の一括マイグレーションは行わない | 純粋な Lazy Migration では古い行の `search_text` が古いまま残り検索結果が一貫しないため、Eager-on-Read に変更。読み込み発生のたびに分散して最大 N 回の単一行 UPDATE で収束する |
| D-12 | items テーブルへの書き込みと FTS5 の更新は SQLite トリガで同一トランザクション内に閉じる | アプリケーションコードによる二重書きの整合崩れを防ぐ |
| D-13 | アプリ全体状態 (現在プロジェクト ID / 現在モジュール / テーマ等) は Day 1 から Zustand で一元管理する。モジュール内ローカル状態は素の useState で扱う | 後から状態管理を導入すると分散した useState の集約に大きな書き換えが発生するため、規律を最初から固定する |
| D-14 | 全ての時刻は JST (Asia/Tokyo, +09:00) を ISO8601 拡張形式 (`YYYY-MM-DDTHH:MM:SS.sss+09:00`) で記録する。アプリケーション側で生成し、SQLite トリガによる自動付与は行わない | 個人ツールであり日本タイムゾーン固定で運用。エクスポートしたファイルが他端末でもタイムゾーン情報を保ったまま解釈できる。SQLite の `CURRENT_TIMESTAMP` は UTC 生成のため、JST 固定方針との整合はアプリ側生成のほうがシンプル |

## 7. 用語定義

| 用語 | 定義 |
|------|------|
| プロジェクト | 項目をまとめる第一級の所属単位。ユーザーが任意に作成・削除できる |
| モジュール | アプリに搭載される個別機能ユニット (Prompt / Link / Color / Hash / Palette 等)。コアからは均一に扱われる |
| コア | プロジェクト管理 / 設定 / ストレージ / モジュールレジストリを提供するアプリ本体 |
| 項目 | モジュールが扱う個別レコード (1つのプロンプト、1つのリンク等) |
