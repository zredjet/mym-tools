# ADR-0028: キャンバスの第 2 段階で、回転・パス・ブーリアン演算を足す

- **Status**: Accepted (統合ブランチ `canvas-stage2` を `main` へマージした時点で有効)
- **Date**: 2026-11-17
- **Deciders**: zredjet
- **Related**: ADR-0006 / ADR-0026 / ADR-0027

## Context

キャンバス (ADR-0026) の第 1 段階 (モックアップとバナー) は `main` に入った。第 2 段階はアイコン・ロゴのための段階で、ADR-0026 はペンツール、パス編集、ブーリアン演算、編集できる形での SVG の取込を挙げていた。

利用者と範囲を詰め、次も入れることにした。

- 全ノードの回転 (第 1 段階は回転を持たない)
- 線の端・角・破線
- 多角形と星のツール、鉛筆 (フリーハンド)
- 線のアウトライン化

回転は、選択と変形、ヒットテスト、スナップ、テキストの編集、描画、書き出しなど、第 1 段階のコードの多くを書き換える。第 1 段階のように「新しいコードは切替まで画面につながない」という進め方ができない。

## Decision

### 保存形式は v3 にする

payload を v3 に上げ、第 2 段階で足すものをすべて v3 に入れる (ADR-0006)。段階の途中で版を何度も上げない。コアスキーマは変えない。

- 回転: 箱を持つノード (frame、矩形、楕円、テキスト、画像、埋め込み SVG、パス) に `rotation` (度、時計回り、箱の中心まわり) を足す。線は端点で、group とブーリアンは子で向きが決まるので持たない
- 線: `cap` (端)、`join` (角)、`dash` (破線) を足す。線の揃えは中央のまま
- パス: 新しいノード `path`。輪郭 (subpath) の並びで、点ごとに前後のハンドルとハンドルの連動の種類を持つ。塗りの規則 (`nonzero` / `evenodd`) を持つ。Figma の vector network (点から 3 本以上の線が出る形) は採らない
- ブーリアン: 新しいノード `boolean`。演算 (合体・型抜き・交差・中マド) と子を持ち、元の図形を残したまま、描くたびに結果を求める (Figma と同じ非破壊の形)。子は矩形・楕円・パス・ブーリアンに限る
- v2 → v3 は、回転 0 と線の既定値 (端 `butt`、角 `miter`、破線なし) を足すだけの書き換えにする。見た目と検索用テキストは変わらない。最初の変換の前のバックアップ (`pre-payload-vector-v3`) は ADR-0027 の規則のとおり取る

多角形・星・鉛筆は、作った時点で普通のパスにする (頂点の数などを後から変えるノードにはしない)。線のアウトライン化と「パスに変換」も、結果は普通のパスになる。

### 埋め込み SVG は、利用者の操作で編集できる形に変換する

SVG ファイルの取込は、これまでどおり埋め込み SVG として置く。埋め込み SVG のノードに「編集できる形に変換」を足し、扱える要素を group・パス・矩形・楕円・線・テキストにする。v1 から引き継いだ作品の埋め込み SVG にも使える。扱えない要素 (マスク、フィルタ、パターン、画像など) を含むときは、何が落ちるかを示して利用者が選ぶ。

ADR-0026 の「v1 の SVG を図形へ分解する変換はしない」は、版の引き上げ (自動の変換) についての決定で、変えない。分解は利用者が選んだときだけ行う。

### 難しい計算も自作する

ブーリアン演算、線のアウトライン化、曲線の当てはめ (鉛筆) は、ADR-0026 のとおり依存を足さずに自作する。ブーリアン演算は非破壊なので、子を動かすたびに求め直す。アイコンの大きさ (曲線 200 本ほど) で 1 回 5 ms 以内を目安にする。求められなかったときも、例外で画面を止めない。

### 統合ブランチで進める

第 2 段階の作業は、`main` から切った統合ブランチ `canvas-stage2` に集める。

- 各セッションは `canvas-stage2` から切った worktree で作業し、`canvas-stage2` 宛ての PR を下書きで出す。オーケストレーターが検証してマージする
- CI は `canvas-stage2` 宛ての PR でも動かす
- `canvas-stage2` では最初から v3 を有効にしてよい。`main` は第 1 段階のままで、いつでもリリースできる
- すべてそろったら、`canvas-stage2` から `main` への PR 1 本で切り替える。マージの前に利用者が実アプリで確かめる

## Alternatives

- **区切ってリリースする** (回転と線 → パスとペン → ブーリアン → SVG の変換): 早く使えるが、区切るたびに payload の版が上がり (v3、v4、v5)、変換・検証・バックアップ・実アプリの確認がその度に要る。利用者が統合ブランチを選んだ
- **ブーリアン演算の結果をすぐパスにする** (破壊的): 実装は軽いが、後から形を直せない。目標の Figma 相当に合わない
- **回転をパスにだけ持たせ、点に焼き込む**: 第 1 段階のコードへの影響は小さいが、矩形やテキストを回したまま編集できない。利用者が全ノードの回転を選んだ
- **SVG を取り込むときに分解する**: 古い作品の埋め込み SVG を編集できる形にする道がなくなる
- **vector network を採る**: 点から何本でも線を出せるが、塗りの面を求める計算 (曲線を含む平面グラフの面の検出) が重く、SVG の `path` とも素直に対応しない。輪郭の並びで足りる用途 (アイコン・ロゴ) なので採らない

## Consequences

- 第 2 段階は第 1 段階と同じくらいの規模になる (テスト込みでおおよそ 1 万〜1 万 5 千行の見積もり。実測ではない)
- `canvas-stage2` は `main` から離れていくので、`main` に入った修正を取り込む必要がある (オーケストレーターが行う)
- 回転したテキストの編集、ブーリアンの子をドラッグしたときの重さ、日本語入力、トラックパッドでのペンの操作は、自動テストでは確かめきれない
- 回転したノードを縦横で違う倍率で拡大縮小すると、矩形・楕円・テキスト・画像は角度を保つため厳密な拡大にならない (パスと線は点を変換するので厳密)
- 新しい版で開いた作品は、第 1 段階の版のアプリでは読めなくなる (ADR-0006 の通常の挙動)

## Acceptance

- v1 と v2 の作品が新しい版で開け、見た目が変わらない。v1・v2 の `vector` を含む古いエクスポートファイルを取り込める
- 回転、パス、ブーリアン、線の端・角・破線を含む作品が保存・再読み込み・JSON の入出力・バックアップで往復する
- Rust と TypeScript の v3 の検証が、共有の契約データ (`payload-v3.json`) で同じ合否になる
- 自動テストと、macOS 実アプリでの受入を分けて記録する。portable ZIP は各 80,000,000 bytes 以下
