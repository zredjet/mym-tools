# ADR-0027: payload の版を上げるときのデータの守り方

- **Status**: Accepted
- **Date**: 2026-11-15
- **Deciders**: zredjet
- **Related**: ADR-0006 (§2.5 の一部をこの ADR が置き換える) / ADR-0007 / ADR-0011 / ADR-0016 / ADR-0026

## Context

ADR-0006 は、payload の版を上げたモジュールの古い行を、読んだときに現行版へ変換して書き戻す (Eager-on-Read) と決めた。変換は戻せない。キャンバス (`vector`) の切替 (ADR-0026) で `current_payload_version` を 1 から 2 に上げ、この経路が初めて実際に動く。実装を確かめると、次の 4 つの危険があった。

1. **旧版へ戻すと、エクスポートが丸ごと止まる**。新しい版で v1 の作品を 1 件開くか、JSON エクスポートを 1 回するだけで、その行は v2 になる。旧版のアプリに戻すと、その作品が開けないだけでなく、アプリ全体の JSON エクスポートが `UnsupportedFuturePayloadVersion` で失敗する。ADR-0006 §2.5 は「Eager-on-Read ではバックアップを取らない」としているので、変換の前の控えがない
2. **変換できない行が、画面を通さない保存で消える**。変換に失敗した行 (今の SVG ポリシーを通らない古い作品など) は v1 のまま残るが、上書きを止めているのは画面 (開けない作品の保存ボタンを出さない) だけで、`update_item` を直接呼べば元の SVG が消える
3. **書き戻しの失敗で、読めるはずの作品が開けない**。ディスクが一杯などで書き戻しの UPDATE が失敗すると、変換はできているのに `Err` になり、v1 の作品が 1 件も開けず、エクスポートも全体が止まる。`data-model.md` §7.6 は「結果は返す」としていたが、実装はそうなっていなかった
4. **変換できなかった行を、エクスポートが黙って書き出す**。§7.6 のとおり古い版のまま書き出す (落とさない) が、何も知らせずに成功するので、取り込む側で初めて失敗に気づく。ADR-0006 §2.5 の「アップグレード失敗となる行はスキップ集計に加える」は、エクスポートでは行を落とす意味にも読め、§7.6 と食い違っていた

## Decision

モジュールを問わない規則として、次の 4 つを足す。

### 1. 最初の変換の前に、バックアップを 1 回取る

起動時、stateful モジュールごとに、`current_payload_version` より古い版の行があり、その版への引き上げのためのバックアップをまだ取っていなければ、pre-op バックアップを 1 回取る。

- ラベル (ファイル名の prefix) は `pre-payload-<module_id>-v<新しい版>` (例: `pre-payload-vector-v2`)。pre-op の 30 件のローテーションに入る
- 取ったことは `meta` の `payload_upgrade_backup.<module_id>` に新しい版の番号で記録する。記録が今の版以上なら、行を調べない。DDL ではなく `meta` の行の追加なので、`db_schema_version` は上げない。`data_revision` も増やさない
- 記録を持つ理由: 変換できない行は古い版のまま残り続けるので、「古い版の行がある」だけで判断すると起動のたびに取ることになる。pre-migration (ADR-0011) は `db_schema_version`、Link / Memo の再所属 (ADR-0016) は移行した行が無くなることがそれぞれ記録の役をしているが、Eager-on-Read は行を少しずつ変えるので、別に記録が要る
- 古い版の行が無ければ取らず、記録もしない。取込は変換してから書くので、後から古い版の行が入ることはない。記録の無い旧版のバックアップをリストアした後は、次の起動でもう一度取る
- 取得に失敗したら、pre-migration と同じく起動を止める (記録もしない。次の起動でもう一度試す)
- 起動の中で、Eager-on-Read が動きうる処理 (画面の起動、エクスポート) より前に行う (`lib.rs` の `prepare_storage`)
- アプリの中のリストア (`core_backup_restore`) の後にも、同じ判定を行う。画面は再起動を促すが、読み込み直して使い続けられるので、記録の無いバックアップを戻すと、次の起動までに開いた古い行がバックアップなしで変換されてしまうため。取得に失敗したら、リストアは済んだことと合わせてエラーを返す

### 2. 変換できない古い行は、上書きを拒否する

利用者の保存は、上書きと同じトランザクションの中で、保存されている行の版を確かめてから書く。確かめるのはストレージの層 (`StorageService::update_item`。引数にモジュールを渡す) で、`ScopedStorage` を通さずにストレージを使う command でも効く。

- 今の版の行: そのまま書く (payload を読まない)
- 古い版の行: 保存されている payload の引き上げを試す。失敗するなら上書きを拒否する (`PayloadUpgradeFailed`、行と `data_revision` は変えない)。成功するなら書く (規則 3 で書き戻しに失敗した行への正規の保存を止めない)
- 新しい版の行 (新しいアプリで書いた行): 拒否する (`UnsupportedFuturePayloadVersion`)。読めない内容を上書きしない
- 削除は止めない (利用者が確認して選ぶ操作のため)
- 引き上げの失敗の扱いは、読み込み・エクスポート・上書きの確認で同じにする。`upgrade_payload` が検証の失敗 (`ValidationFailed`) を返したときも「変換できない」(`PayloadUpgradeFailed`) として扱う (`ModuleError::into_upgrade_error`)

### 2.1 変換の結果は、画面でも開けること

モジュールの変換 (と JSON の取込) が受け付けた新しい版の payload は、画面 (TypeScript) の検証も受け付けること。Rust では通るのに画面では開けない payload ができると、行はもう新しい版で戻せず、元の内容を取り出す口 (変換できない古い行のためのもの) も使えない。Rust と画面で結果が分かれうる入力は、Rust の検証で拒否する (変換なら失敗にして古い版のまま残る)。キャンバスでは、SVG の文字の規則 (XML 1.0 の Char にない文字と、U+0085 をそのまま書いたものの拒否) を Rust と画面の SVG ポリシーで同じにし、共有の契約データ (`validation-fixtures.json`、`payload-v2.json`) で合否の一致を確かめる

### 3. 書き戻しに失敗しても、変換した結果は返す

Eager-on-Read の書き戻しの UPDATE が失敗したら、ログに残し、変換した結果を返す。行は古い版のまま残り、次に読んだときにもう一度変換する。エクスポートも変換した結果を書き出す。`data-model.md` §7.6 の「永続化未完了」のフラグと UI の通知は作らない (保存は規則 2 で通り、次の読み込みで書き戻しを再び試すため)。

### 4. エクスポートで変換できなかった行を知らせる

エクスポートは、変換に失敗した行を古い payload と版のまま書き出し (§7.6 のまま、落とさない)、その行の ID・モジュール・タイトル・版・理由を `ExportSummary.not_upgraded` で返す。完了の表示に「n 件は新しい形式に変換できないため、元の形式のまま書き出しました。このファイルを取り込むと、これらは失敗として数えられます」と出す。変換の失敗でないエラー (DB の読み取りの失敗、モジュールの内部エラー) では、これまでどおりエクスポートを止める。

### ADR-0006 のうち置き換えるところ

- §2.5「古い payload で『アップグレード失敗』となる行はスキップ集計に加える」: 規則 4 に置き換える (行は落とさず古い版のまま書き出し、`not_upgraded` で知らせる)
- §2.5「pre-op backup は取らない」: エクスポートの中では今も取らない。ただし、どの経路の変換よりも前に、規則 1 の起動時のバックアップを取る
- §2 の表「失敗時の取扱い」の「UPDATE 失敗」: 規則 3 に置き換える (呼び出し側へ伝えず、変換した結果を返す)

### ADR-0006 のうち、今回は行わないこと

- §2.3 の検索インデックス再構築 (`core_rebuild_search_index`) と §2.4 の版の上昇の通知 (`modules.<id>.last_seen_payload_version`) は実装されていない。キャンバスの v1 と v2 の `search_text` は、U+0085 を含む作品のほかは同じ値になる (v2 の `text` は v1 の SVG から同じ規則で求める) ので、読まれていない v1 の行も検索の結果はほぼ変わらない。今回は作らず、次に検索用テキストが大きく変わる版の上げで改めて決める

## Alternatives

- **起動時にすべての古い行を一括で変換する**: ADR-0006 §3.2 で却下した理由 (起動の待ち、D-03) がそのまま当てはまる。バックアップだけを先に取れば、変換の時期は今のままでよい
- **記録を `settings.json` に置く**: バックアップをリストアすると DB の中身は変わるが設定は残り、「この DB の古い行の控えを取ったか」と合わなくなる。DB の状態なので `meta` に置く
- **バックアップのファイルの有無で判断する**: pre-op は 30 件でローテーションされ、消えた後に起動のたびに取り直すことになる
- **上書きの確認を画面だけに任せる**: 画面を通さない呼び出し (将来のモジュール、テスト、別の画面) で元の内容が消える。保存の境界であるバックエンドで止める

## Consequences

- 新しい版を最初に起動したとき、古い版の行があるモジュールごとに 1 回、バックアップの分だけ起動が遅くなる。ディスクが足りなければ起動しない (pre-migration と同じ)
- 旧版へ戻すときは、旧版のアプリで `pre-payload-<module_id>-v<版>` (または利用者が取ったバックアップ) をリストアすれば、変換の前の状態に戻る
- 変換できない行は、どの経路でも上書きされない。中身はモジュールごとの口 (キャンバスでは「元の SVG を書き出す」) で取り出し、要らなければ削除する
- `meta` に `payload_upgrade_backup.<module_id>` の行が増える。古い版のアプリはこの行を読まない
- 防がない道: 記録が付いた後に旧版のアプリへ戻し、旧版で古い版の作品を作ってから新版に戻すと、記録は付いたままなので、その作品はバックアップなしで変換される。旧版へ戻すときは、戻した版で手動バックアップを取ってから新版に戻す
- `pre-payload-<module_id>-v<版>` は pre-op のバックアップなので、ほかの pre-op (取込、プロジェクトの削除、リストアなど) が 30 件を超えると、古い順に消える。記録は残るので取り直さない。長く旧版へ戻せるようにしたいときは、利用者が手動バックアップ (`manual`、自動では消えない) を取る

## Acceptance

- v1 の行がある DB で起動すると `pre-payload-vector-v2-…` が 1 回だけ取られ、中身は v1 のまま。2 回目の起動では取らない。取得に失敗すると起動が止まり、記録は残らない。記録の無いバックアップをアプリの中でリストアすると、その場でもう一度取る
- 変換できない v1 の行に `update_item` を呼ぶと (`ScopedStorage` を通しても、`StorageService` を直接呼んでも) 拒否され、行と `data_revision` が変わらない。新しい版の行も拒否される。変換できる v1 の行は書ける。`upgrade_payload` の `ValidationFailed` は、読み込み・エクスポート・上書きのどれでも「変換できない」になる
- Rust の変換が受け付けた v2 は、画面の `validatePayload` も受け付ける (共有の契約データで確かめる)
- 書き戻しが失敗しても、読み込みとエクスポートは変換した結果を返し、行は v1 のまま
- 変換できない行を含むエクスポートは成功し、`not_upgraded` にその行が入り、完了の表示に出る
