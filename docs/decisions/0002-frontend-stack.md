# ADR-0002: フロントエンド技術スタック (React + TypeScript + shadcn/ui + Zustand)

- **Status**: Accepted
- **Date**: 2026-04-29
- **Deciders**: zredjet
- **Related**: ADR-0001 (Tauri v2) / `requirements.md` D-09 / D-13 / `architecture.md` §2.3

---

## 1. Context

ADR-0001 で Tauri v2 を採用することが決定し、その上に乗るフロントエンド層を決める必要がある。
本 ADR ではフロントエンドの基盤となる以下 4 レイヤを決定する:

1. **ベースフレームワーク** — UI を書く言語/ランタイム
2. **UI コンポーネントライブラリ** — ボタン / 入力 / モーダル等の見た目と振る舞いの基盤
3. **状態管理** — アプリ全体状態 (現在プロジェクト ID / テーマ / 設定) の扱い
4. **ルーティング** — モジュール内の画面遷移と URL 表現

選定の制約 (`requirements.md` / `architecture.md` から):

| 制約 | 趣旨 |
|------|------|
| 軽量性 | バンドルサイズ・メモリ常駐を抑える |
| モジュール独立 | UI レイヤでもモジュールが他モジュールに依存しない構造を維持 |
| 個人開発 | 学習コスト・ドキュメント量・AI 補完の効きやすさが効く |
| 日本語 UI のみ | i18n インフラ不要 |
| アクセシビリティ | キーボード操作と Radix Primitives ベースのコンポーネントが扱いやすいこと |

## 2. Decision

Phase 1 のベースラインとして以下のバージョンを確定する。
package.json の semver レンジ表記 (`^X.Y.Z`) で記載しているが、**マイナーアップデートは取り込み可、メジャーアップデートは ADR 改訂を要する**ものとする。

| レイヤ | パッケージ / 製品 | バージョン |
|-------|---------------|----------|
| ベースフレームワーク | `react` / `react-dom` | `^19.0.0` |
|  | `typescript` (strict) | `^5.7.0` |
| UI コンポーネント | shadcn/ui | CLI 経由でコピー (バージョン非固定 / 取り込んだ時点のスナップショット) |
|  | `tailwindcss` | `^4.0.0` |
|  | `@radix-ui/react-*` | shadcn が依存する個別バージョンに従う |
| 状態管理 | `zustand` | `^5.0.0` |
| ルーティング | `react-router` (`react-router-dom`) | `^7.0.0` (library mode、SSR 機能は使わない) |
| ビルド | `vite` | `^6.0.0` |
| フォーム | `react-hook-form` | `^7.50.0` |
|  | `zod` (バリデーション) | `^3.23.0` |
| Markdown (D-09) | `react-markdown` | `^9.0.0` |
|  | `remark-gfm` | `^4.0.0` |
|  | `rehype-highlight` | `^7.0.0` (Shiki ではなく **rehype-highlight に確定** / Q-16 解決) |

**Markdown ライブラリの最終確定 (Q-16)**:
- **rehype-highlight** を採用 (highlight.js ベース)
- 採用理由: バンドルが軽い (Shiki はテーマ JSON を同梱するため重め) / CSS テーマ切り替えで完結し JS 側のテーマ管理が要らない / Phase 1 ではプロンプト本文の可読性向上が目的でテキストメイト級ハイライト精度は不要
- Shiki は将来「コード本文を扱う別モジュール (例: スニペット管理)」を追加する局面で再評価する

## 3. Alternatives Considered

### 3.1 ベースフレームワーク

| 候補 | 評価 |
|------|-----|
| **React (採用)** | エコシステム最大。shadcn/ui の前提。AI 補完・ドキュメント量も最厚。`react-markdown` 等の Phase 1 で必要なライブラリが揃う |
| Vue 3 | 学習コスト低・テンプレート構文が読みやすいが、shadcn/ui の React 専用 を捨てることになる。Tauri との接続例も React の方が多い |
| Solid | 細粒度リアクティビティで高性能だがエコシステムが薄く、shadcn/ui 同等の UI ライブラリを別途選ぶ必要が出る |
| Svelte / SvelteKit | コンパイル時最適化が魅力だが、SvelteKit は SSR 前提の構成が多くデスクトップアプリ用途には過剰。UI ライブラリも React より選択肢が少ない |
| Angular | 個人ツール規模に対しフルフレームワーク的な思想が重く、学習・運用コストが過剰 |

→ **React 採用**。shadcn/ui との結合と、AI 補助込みでの開発速度が決定打。

### 3.2 UI コンポーネントライブラリ

| 候補 | 評価 |
|------|-----|
| **shadcn/ui (採用)** | コンポーネントを npm でなく**コピーしてプロジェクトに取り込む**方式。未使用分はそもそも存在しないので tree-shaking 不要。Radix UI ベースで a11y 担保。Tailwind 統合済み |
| Mantine | 100+ コンポーネント + hooks で完成度高いが、バンドルサイズが shadcn 路線より重い。「Mantine ぽい見た目」が出やすい |
| Chakra UI | Emotion ベースで CSS-in-JS のランタイムオーバーヘッド有。軽量性方針と微妙にズレる |
| Ant Design | エンタープライズ志向で重厚。個人ツールには過剰 |
| MUI | 同上。Material Design の見た目が個人ツールの空気に合いにくい |
| Radix UI 単体 + 自前 Tailwind | shadcn/ui のさらに低レイヤ。最小バンドルだが開発工数が大きい |

→ **shadcn/ui 採用**。Radix UI のコピーアップグレード型に Tailwind を組み合わせた方式は、軽量性とカスタマイズ性のバランスが Phase 1 の方針と最も合致する。

### 3.3 状態管理

| 候補 | 評価 |
|------|-----|
| **Zustand (採用、Day 1)** | 約 3KB / Provider 不要 / フックベース API / devtools サポート。アプリ全体状態 (プロジェクト/モジュール/テーマ) の管理に過不足ない |
| 素の Context + useState | 0 依存だが、状態が分散すると後付けで Zustand に集約するときの書き換えコストが大きい (D-13 でこの判断は確定済み) |
| Redux Toolkit | reducer / action / slice の概念が個人ツール規模にはオーバーヘッド。Zustand の半分以上の機能は不要 |
| Jotai | atom ベースが魅力だが、本アプリのアプリ全体状態は数個でフラットなので atom 化が過剰 |
| Recoil | Meta が積極開発を停止しており選定リスクあり |
| TanStack Query | サーバ状態管理ライブラリだが、本アプリは IPC で同期的にデータを取り直すため適合しない |

→ **Zustand 採用** (D-13 で確定済み。本 ADR で改めて記録)。

### 3.4 ルーティング

| 候補 | 評価 |
|------|-----|
| **React Router v6+ (採用)** | 最大手・ドキュメント量・shadcn/ui の examples で前提とされる場合が多い。動的ルート + ネストルートが揃っている |
| TanStack Router | ファイルベース・型安全ルーティングが魅力だが、エコシステムが React Router より薄く、Phase 1 で導入する利得が薄い |
| Wouter | 軽量 (1.5KB) だが、Phase 1 で必要な動的セグメント / ネスト程度なら React Router でもバンドル差は誤差。情報量で React Router |
| 自前ルーティング | URL バーがないデスクトップアプリでは現実的だが、ブラウザ履歴 / 戻る進む / ディープリンクの自前実装が手間 |

→ **React Router v6+ 採用**。

### 3.5 ビルドツール

Vite を採用。Tauri v2 の `create-tauri-app` テンプレートが Vite を前提としており、HMR・TS サポート・プラグインエコシステムが標準的。代替として Webpack / Turbopack / Rsbuild も存在するが、Tauri 公式テンプレートと外れる必要性が無い。

### 3.6 フォーム

React Hook Form + Zod (バリデーション) + shadcn/ui の Form ラッパ。
shadcn/ui のドキュメント・サンプルがこの組み合わせで書かれており、Phase 1 で別の組み合わせを採る理由が無い。

## 4. Consequences

### 4.1 Positive
- **shadcn/ui のコピー方式により、未使用コンポーネントは存在しない** → バンドルサイズ最小化と整合
- React + TypeScript + Tailwind は AI 補助による生産性が最も高い組み合わせの 1 つ。個人開発者の手数を最小化できる
- Zustand を Day 1 から導入するため、状態の置き場所が最初から固定され、後で分散した useState を集約する書き換えが発生しない (D-13 の意図)
- Radix UI 由来でキーボード操作 / a11y が標準で堅い
- Tauri v2 + Vite + React のテンプレートが公式に整備されており、初期セットアップで詰まりにくい

### 4.2 Negative / Risks
- **shadcn/ui のアップデート反映は手動**: コンポーネントをコピーしてプロジェクトに置く方式のため、上流のバグ修正・改善を取り込むには `shadcn-ui CLI` で再コピーするオペレーションが必要。Phase 1 では問題ないが、長期保守でルーチン化が要る
- **Tailwind のクラス羅列が肥大化** すると JSX の可読性が落ちる。コンポーネント分割で吸収する規律が要る
- **React の同時並行レンダリング (concurrent features)** をフル活用するには学習コストがあるが、個人ツール規模では Phase 1 では不要 (使わなくても問題ない)
- **Zustand のミドルウェア (persist 等) を後から足す場合の再設計** が小規模に発生し得る。最初から `persist` ミドルウェアを使うかは実装時に判断

### 4.3 Neutral
- TypeScript の `strict: true` を初期設定で有効にする。型補助の恩恵を最大化するため、後から外さない方針
- ESLint + Prettier の構成は Tauri 公式テンプレートのデフォルトに従う (詳細はビルド設定 ADR を別途切るほどでもないため本 ADR で確定)

### 4.4 Known Concerns / 将来見直しが要りうる判断

本 ADR で確定したが、Phase 1 進行中に再評価する可能性が比較的高い判断を**監視対象**として残しておく。
「今すぐ覆す」ではなく「動かし始めたら違和感が出るかもしれない」項目。

#### 4.4.1 React Router 採用 vs TanStack Router

- 採用理由は §3.4 の通り (情報量・shadcn 例との親和性)
- **懸念**: TanStack Router の型安全ルーティング (URL パスの型推論 + 検索パラメータの型付け) は本来 TS strict 環境と非常に相性が良い。後から「URL 周りの型エラーで助かった可能性」を失っているかもしれない
- **再評価のタイミング**: Phase 1 で 2 モジュール程度実装した段階で、URL パス周りで型ヒントが欲しかった場面の数を振り返る。多発していれば本 ADR を 2.0 で改訂し、TanStack Router へ切替
- **切替コストを抑える実装規律**: ルート定義を「画面定義オブジェクトの配列」として 1 か所にまとめる (`src/routes/index.ts`)。React Router 固有の API はその抽象の内側だけで使う。これで切替時の影響範囲を限定できる

#### 4.4.2 React Hook Form + Zod が Phase 1 で過剰の可能性

- 採用理由は §3.6 の通り (shadcn/ui Form ラッパが前提とする)
- **懸念**: Phase 1 のフォームは「プロンプト編集 / リンク編集 / カラー編集 / プロジェクト編集」程度で、複雑な依存関係を持つフィールドは無い。素の useState + 手書き検証で十分だった可能性がある
- **再評価のタイミング**: 各モジュール実装完了時に「RHF + Zod が真に効いた場面」(動的バリデーション / フィールド間依存 / 非同期検証など) の有無をレビュー。1 つも無ければ本 ADR を改訂し RHF を外す選択肢を残す
- **二重管理の予防**: Zod スキーマと TS 型を別々に書かず、`type X = z.infer<typeof xSchema>` で型を導出する規約を最初から固定する。フォーム定義 + 検証 + 型が 1 つのスキーマから派生する形を強制

#### 4.4.3 Zustand `persist` ミドルウェアを Day 1 採用しない

- 本 ADR ではアプリ全体状態の永続化に Zustand `persist` を使うかは**実装時判断**とした
- **懸念**: 実装段階で「Zustand state を永続化したい」と思った瞬間に `persist` を追加する選択肢があるが、Phase 1 のアプリ全体状態 (`last_opened_project_id` 等) は既に `settings.json` 経由で永続化される設計 (data-model.md §11)。**永続化経路を 2 系統作ると整合性が崩れる**
- **判断軸**: 永続化が必要な状態は 100% `settings.json` 経由とし、Zustand `persist` は使わない方針を**本 ADR の補足として確定**する
- もし将来 `persist` を採用する場合は、`settings.json` との対象キー重複を排除する設計を ADR で明示してから入れる

#### 4.4.4 Validation Criteria「1 機能あたり数十 KB 以内」は感覚値

- §6 の数値 (バンドルサイズの目安) は実測未根拠
- **懸念**: shadcn コンポーネントは個別軽量だが、Phase 1 完了時の累計でこの目安に収まるかは未検証
- **再評価のタイミング**: Phase 1 で 2 モジュール実装完了時にバンドル分析 (`vite-bundle-visualizer` または `rollup-plugin-visualizer`) を 1 回走らせる。実測値が大幅に違うなら本 ADR §6 を 1.x で改訂
- **悪化したときの逃げ道**: shadcn コンポーネントの取り込みを必要最小限に絞る / Tailwind の未使用クラス除去 (本来 v4 で自動) を確認 / 本当にダメなら一部の重いコンポーネント (DatePicker 等) を別実装に差し替え

## 5. Mitigations

| リスク | 対策 |
|-------|------|
| shadcn/ui の手動アップデート漏れ | 月次レビューのチェック項目に「shadcn コンポーネントの上流変更を追う」を追加 (Phase 2 以降のメンテナンスタスク化) |
| Tailwind クラス羅列の肥大 | 共通スタイルは shadcn/ui コンポーネントのバリアント / `cn()` ヘルパで吸収。`@apply` の多用は避ける |
| Zustand の再設計コスト | アプリ全体状態を扱う store を 1 つに集約 (`useAppStore`) し、selector 関数経由でしかアクセスさせない規律を初期から固定 |

## 6. Validation Criteria

- フロントエンド成果物 (Tauri がバンドルする `dist`) のサイズが、shadcn コンポーネントを増やしても**プロジェクトの 1 機能あたり数十 KB 以内**で収まること
- React Router でモジュール間 / モジュール内ルーティングが破綻なく動くこと
- Zustand store が「アプリ全体状態のみ」のスコープに収まり、モジュール内状態が紛れ込んでいないこと (Phase 1 終了時点でレビュー)
- 主要 UI 操作がキーボードのみで完結すること (キーボード操作のテストシナリオを Phase 1 に含める)

達成できない場合は、対象レイヤの ADR を別途起こして見直す。
