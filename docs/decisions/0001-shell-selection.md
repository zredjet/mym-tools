# ADR-0001: デスクトップシェルとして Tauri v2 を採用する

- **Status**: Accepted
- **Date**: 2026-04-26
- **Deciders**: zredjet
- **Related**: `requirements.md` §1.3 / §3.1 / §3.2 / §3.8 / D-04

---

## 1. Context

本プロジェクトは Windows / macOS 両対応のローカルデスクトップ GUI ツールとして開発される。
要件 (`requirements.md`) で確定した制約のうち、シェル選定に影響する主なものは以下:

| 制約 | 値 / 趣旨 |
|------|----------|
| 起動時間 | コールドスタート 1.5 秒以内 (中位スペック PC) |
| メモリ常駐 | 起動直後 100MB 以下 |
| インストーラサイズ | 30MB 以下 |
| 対応 OS | Windows 10/11、macOS 12+。Linux はサポート対象外 |
| 配布方式 | コード署名あり / **自動更新なし / portable 差し替えで完結** (D-04) |
| データ配置 | アプリ実行ファイルと別ディレクトリ (OS 標準のユーザーデータディレクトリ) |
| 開発体制 | 個人開発 / 単一コードベースで Win/Mac 両対応 |

これらの制約のもとで、デスクトップアプリのシェル (ウィンドウ + WebView/レンダラ + バックエンドバインディング) として何を採用するかを決定する。

## 2. Decision

**Tauri v2** を採用する。

- フロントエンド層 (UI): React + TypeScript を Tauri の WebView 上で動作させる
- バックエンド層 (永続化 / OS 連携 / 重い計算): Rust で実装し、Tauri の IPC (`invoke` / `emit`) でフロントと通信する
- WebView は Tauri が OS 標準のものを利用する: Windows では Microsoft Edge WebView2、macOS では WKWebView

## 3. Alternatives Considered

### 3.1 Electron

最も一般的なクロスプラットフォーム デスクトップシェル。Chromium と Node.js を同梱する。

- ✅ 大きなコミュニティ・豊富な事例・成熟した周辺エコシステム
- ✅ Web 技術スタックがフルに使え、開発速度が出る
- ❌ **同梱バイナリが極めて大きい** (Chromium だけで 100MB 以上、最小構成のアプリでも 100〜150MB)
- ❌ **メモリフットプリント** が大きい (空アプリで 200〜400MB)
- ❌ インストーラサイズ 30MB / メモリ 100MB の要件を**到底満たせない**

→ **却下**。要件の軽量性目標と本質的に相容れない。

### 3.2 Wails (v2)

Go バックエンド + OS 標準 WebView。Tauri と同じ「OS WebView を借りる」アプローチ。

- ✅ Tauri と同じく軽量バイナリ
- ✅ Go の開発体験は良好
- ❌ Rust ではなく Go バックエンド。SQLite + JSON ハイブリッド方針 (D-10: rusqlite 採用) と整合しない
- ❌ Tauri v2 と比較してコミュニティ規模・プラグイン充実度で見劣りする
- ❌ macOS の WebView 統合 / コード署名 / 配布周りのドキュメントが Tauri ほど整っていない

→ **却下**。技術スタック (rusqlite / Rust エコシステム) との親和性で Tauri が優る。

### 3.3 Flutter Desktop

Dart + 自前レンダリングエンジン (Skia / Impeller)。

- ✅ モバイル含めた強力なクロスプラットフォーム対応
- ✅ UI のレンダリング品質が OS 間で完全に均一
- ❌ **自前エンジンを同梱** するためバイナリが大きい (40〜80MB の起点)
- ❌ デスクトップ向け成熟度はモバイルと比較して低く、OS ネイティブ機能 (ファイラー連携等) のプラグインが薄い
- ❌ Dart エコシステムは Web 系 OSS との接続性が乏しい (例: Markdown レンダラの選択肢が React 系より狭い)
- ❌ 個人ツール規模では「均一な独自レンダリング」よりも「OS 標準の見た目に馴染む」方が望ましい

→ **却下**。軽量性 + Web エコシステム活用の両立で Tauri が優る。

### 3.4 ネイティブ実装 (Win32 / AppKit を別個に)

各 OS のネイティブ API + ネイティブ言語 (C++ / Swift) で個別実装。

- ✅ 究極の軽量性とパフォーマンス
- ✅ 各 OS の HIG に最大限従える
- ❌ **Win/Mac で 2 つのコードベース**を維持するコストが個人開発で許容不能
- ❌ 単一コードベースで Win/Mac 両対応する要件を満たせない

→ **却下**。本要件のスコープ外。

### 3.5 Qt + QML / C++

伝統的なクロスプラットフォーム GUI フレームワーク。

- ✅ 成熟・高性能・OS ネイティブ風の見た目
- ❌ ライセンス (LGPL/GPL/商用) の選択が複雑化する
- ❌ 個人ツールに対して開発エコシステムが過剰 (C++ の所要学習・ビルドツール整備が重い)
- ❌ Web エコシステムの便利な OSS (Markdown レンダラ / シンタックスハイライト等) と接続しにくい

→ **却下**。個人ツール規模に対してオーバーキル。

## 4. Consequences

### 4.1 Positive
- **軽量性目標 (起動 1.5s / メモリ 100MB / インストーラ 30MB) が現実的に達成可能**な唯一のフレームワーク
- フロント (React + TS) とバック (Rust) の分離が IPC で明確になり、軽量性志向のアーキテクチャと相性が良い
- Rust バックエンドにより `rusqlite` を始めとする SQLite 周りのエコシステムが直接使え、データモデル設計 (D-10 / D-12) と整合する
- macOS の WKWebView / Windows の WebView2 を借りる方式により、各 OS のセキュリティアップデートが OS 経由で適用される (アプリ更新と独立)
- Tauri v2 の portable バンドル / NSIS / DMG 配布が D-04 (手動差し替え更新) と整合する

### 4.2 Negative / Risks
- **WebView の OS 間差異**: WebView2 (Chromium 系) と WKWebView (WebKit 系) で挙動が異なる場面がある (例: 一部の CSS / レンダリング差 / Fetch 挙動)。両 OS で並行検証が必要
- **Tauri v2 のエコシステム成熟度**: v1 と比べて API が再設計されており、プラグインや事例が成熟途上。破壊的変更のリスクが Electron より高い
- **コード署名の必須化**: macOS Gatekeeper と Windows SmartScreen 対策で開発者証明書が必須になる (Apple Developer 年額 / Windows コードサイニング証明書のコスト)
- **Stack Overflow / AI 補完の知識量** が Electron と比べて少ない (が Rust + Web の組み合わせなのでそれぞれの個別解説で補える)

### 4.3 Neutral
- Tauri 固有の概念 (`invoke` コマンド / `emit` イベント / `tauri.conf.json` 許可リスト / プラグイン) を学習する必要がある (Phase 1 序盤の学習コスト)
- Rust 側のビルドが Cargo 経由になるため、CI ビルド時間は Electron 比でやや長い (個人プロジェクトでは許容範囲)

## 5. Mitigations

| リスク | 対策 |
|-------|------|
| WebView 差異 | Phase 1 早期に「主要画面を Win / Mac 両方で目視確認する」チェックリストを作る |
| Tauri v2 破壊的変更 | バージョンを安定リリースにピン留めし、bump は意図して行う。`Cargo.lock` / `package-lock.json` をコミット |
| コード署名コスト | ADR-0008 (配布) で具体的なコスト・取得手順を整理 |
| 学習コスト | Phase 1 最初期に M-Hash の `hash_compute_text` 1 コマンドで Tauri IPC の往復を PoC (`module-contract.md` Q-22 と兼ねる) |

## 6. Validation Criteria

本決定が想定通りに機能しているかを判定する基準。Phase 1 終了時点でレビューする:

- ビルド済みインストーラサイズが 30MB を**大幅には**超えていないこと (上ブレ 1.5 倍程度までは許容)
- アプリ起動時のメモリ常駐が 100MB を**大幅には**超えていないこと (同上)
- Win / Mac いずれでも主要画面が崩れず動作すること
- IPC 経由のコマンドが安定して動作し、`generate_handler!` の集中登録方式 (Q-22) で運用できること

達成できない場合は本 ADR を Superseded とし、別フレームワークへの移行 ADR を起こす。
