# ADR-0007: ローカルバックアップ戦略 (Online Backup API + data_revision)

- **Status**: Accepted
- **Date**: 2026-04-30
- **Deciders**: zredjet
- **Related**: ADR-0003 (rusqlite + bundled SQLite) / ADR-0005 (JST_FILENAME_TIMESTAMP) / ADR-0006 (Eager-on-Read) / `requirements.md` C-06 / D-04 / D-05 / D-07 / `data-model.md` §13

---

## 1. Context

ローカル個人ツールにおけるデータ保護を 2 系統の仕組みで担う:

| 仕組み | 役割 | 担当 ADR / 文書 |
|-------|-----|----------------|
| エクスポート JSON | **可搬性** (端末移行 / 共有 / 長期アーカイブ / Git 管理) | C-06 / D-05 / D-07 / `data-model.md` §12 |
| **DB バックアップ** | **ローカル復旧** (誤削除 / 破壊的操作前の安全網 / 短期スナップショット) | **本 ADR** / `data-model.md` §13 |

両者は補完関係にあり、どちらか一方では十分ではない:
- エクスポート JSON は人間可読で他端末でも開けるが、毎回ユーザーが明示実行する必要があり、頻度が低い
- DB バックアップは自動・高頻度に取れるが、可搬形式ではない (バイナリ SQLite)

本 ADR では DB バックアップ側の戦略を確定する。

選定に効く制約:

| 制約 | 趣旨 |
|------|------|
| WAL モードでの整合性 | data-model.md §2 のとおり WAL 動作中は `data.sqlite` 単独コピーで整合性を欠く可能性がある |
| 排他制御 (data-model.md §13.7) | バックアップ取得は writer mutex 経由で他の書き込みと直列化 |
| ストレージ容量 | 個人 PC の SSD を圧迫しない範囲に抑える (世代数とローテーション設計) |
| ユーザー操作の最小化 | 自動取得の動線は黙って動くべき / 重要操作前のセーフティネットは自動化される |
| 復旧の確実性 | 破壊的操作の直前バックアップが最低 1 件は残ること |

## 2. Decision

| 項目 | 採用 |
|-----|------|
| 取得方法 | **SQLite Online Backup API** (`rusqlite::backup`) を使用。ファイルコピーは禁止 |
| 形式 | SQLite データベースファイル (`.sqlite`)、別の SQLite クライアントから直接読める |
| データ変更検知 | `meta.data_revision` カウンタ (StorageService のコミット単位で +1) |
| バックアップ種別 | **3 種類**: auto (日次自動) / pre-op (破壊的操作直前) / manual (ユーザー手動) |
| 保存先 | `<userdata>/backups/{auto,pre-op,manual}/` |
| 命名 | `<type-prefix>-<JST_FILENAME_TIMESTAMP>-r<revision>.sqlite` (ADR-0005 の `JST_FILENAME_TIMESTAMP`) |
| ローテーション | auto: 最新 10 / pre-op: 最新 30 / manual: 自動削除なし |
| 排他制御 | バックアップ取得は writer mutex 経由 (data-model.md §13.7) |
| リストア後 | 必ずアプリ再起動 (DB 接続再生成のため) |
| キャンセル可否 | 取得は短時間につき Phase 1 では非対応 / リストアはキャンセル要求受付するが writer トランザクション中は実効キャンセル不可 (詳細は ADR-0009 §1 表 / §7.2) |
| Export JSON との役割分離 | エクスポート JSON は「可搬」、本 ADR の DB バックアップは「ローカル復旧」。両者は独立に運用 |

詳細仕様は `data-model.md` §13 を正とする。本 ADR は**選定の根拠と却下した代替案**を記録する。

### 2.1 取得方法 (Online Backup API)

`rusqlite::backup::Backup` を使用してオンライン (アプリ稼働中) のままバックアップを取得する。

```rust
// 概念コード
use rusqlite::backup::Backup;

fn take_backup(src: &Connection, dst_path: &Path) -> Result<()> {
    let mut dst = Connection::open(dst_path)?;
    let backup = Backup::new(src, &mut dst)?;
    backup.run_to_completion(/*pages*/ 1024, /*pause*/ Duration::from_millis(0), None)?;
    Ok(())
}
```

- WAL 含めた最新コミット状態が取得される (`data.sqlite` 単独ファイルコピーと違って整合性が保証される)
- 取得中もアプリは通常通り読み書きできる (Online Backup API はオンラインで動作)
- 取得した `.sqlite` ファイルは **別の SQLite クライアント (sqlite3 CLI / DB Browser for SQLite 等) で直接開ける**

### 2.2 `data_revision` による無駄バックアップの抑止

`meta.data_revision` カウンタ:
- 型: 整数。StorageService のコミット単位で +1
- ユーザー編集を伴う操作のみ増分: item / project の create / update / delete / import 投入 / DB schema migration 適用
- **増分しない操作**: Eager-on-Read による自動アップグレード / `core_rebuild_search_index` / meta 自体への書き込み (ADR-0006 §2)

**実装上の型注意**:
- SQLite の INTEGER カラムは **signed 64-bit** (rusqlite は `i64` にマッピング)
- Rust 側も **`i64` で扱う**ことを規約とする。`u64` は使わない (SQLite 境界での型キャストが必要になり、ヒューマンエラーの温床になる)
- `i64` の最大値 (約 9.2 × 10^18) は個人ツール規模で**実質無限** (1 秒に 100 万コミットしても 30 万年で枯渇)。オーバーフローを心配する必要はない

#### `last_backup_revision` と `last_auto_backup_at` の意味

両者の責務を明確に分離する。

| meta キー | 何を表すか | 更新タイミング |
|---------|--------|------------|
| `last_backup_revision` | **最後に成功した任意種別の DB バックアップ**時点の `data_revision` | auto / pre-op / manual いずれかが成功するたびに更新 |
| `last_auto_backup_at` | 直近の **auto** バックアップ取得時刻 (JST_ISO8601) | auto 取得時のみ更新。pre-op / manual では更新しない |

意図:
- `last_backup_revision` は「最後にどこかでバックアップが取れていれば auto を急いで取らなくてよい」という判定に使うため、種別を問わず最新を保持
- `last_auto_backup_at` は「24 時間に 1 回」という時刻ゲート専用。pre-op / manual の取得で 24 時間タイマーをリセットしてしまうと、本来取りたい日次自動が抑止されるため、auto 専用で持つ
- 結果として「pre-op 直後の起動で auto は取られない (`data_revision == last_backup_revision` のため不要)」という体験になる。これは設計上の正しい挙動 (バックアップ整合性を保つために重複取得を避ける)

### 2.3 3 種類のバックアップ

#### auto (日次自動)
- アプリ起動時、以下を**両方**満たす場合に取得:
  - `data_revision != last_backup_revision` (前回以降に変更がある)
  - 直近の `last_auto_backup_at` から **24 時間以上経過** (もしくは未取得)
- ローテーション: 最新 **10 世代**
- 命名 prefix: `auto`

#### pre-op (破壊的操作直前)
- 以下の操作実行前に**必ず**バックアップ取得 (取得失敗時は当該操作を中止):
  - project 削除 (`pre-delete-project-<projectId>`)
  - import 実行 (`pre-import`)
  - DB schema migration 適用 (`pre-migration-v<N>`)
  - restore 実行 (`pre-restore`)
  - `core_rebuild_search_index` (`pre-rebuild-search-index-<module_id>` / `-all`) ← ADR-0006 §2.3 で追加
- ローテーション: 最新 **30 世代**
- **対象操作が失敗した場合の扱い**: pre-op バックアップ取得後に対象操作 (project 削除等) が失敗しても、**取得済みバックアップは削除しない**。失敗直前の状態を示す診断資料として残し、必要に応じてユーザーが復元に使える。ローテーションで自然に古くなったときに削除される

#### manual (ユーザー手動)
- 設定画面の「今すぐバックアップ」ボタンから取得
- 命名 prefix: `manual`
- **自動ローテーションしない**。ユーザーが UI から個別削除

### 2.4 リストア (復元)

#### 2.4.1 リストア前の整合性検証

選択されたバックアップファイルに対し、リストア実行**前に** **`PRAGMA integrity_check`** を 1 回実行する。

- DB サイズによって数秒かかる可能性があるため、UI には **進行中表示** (スピナー / プログレス) を出す
- 整合性チェックが失敗した場合: リストアを**中止**し、ユーザーに**別のバックアップファイル選択を促す** (エラーメッセージで該当ファイルが破損している旨を通知)
- 成功した場合のみ次のリストア手順 (§2.4.2) に進む

#### 2.4.2 リストア手順

整合性検証通過後の復元手順 (data-model.md §13.6 と整合):

1. UI を「メンテナンスモード」に遷移、すべての画面で操作不可
2. 進行中の書き込みトランザクション完了を待つ (writer mutex 取得)
3. すべての読み取り接続をクローズ
4. WAL ファイル (`-wal`, `-shm`) をクローズ・削除
5. **pre-restore バックアップを取得** (元の状態に戻れるように)
6. 選択されたバックアップファイルを Online Backup API で `data.sqlite` に書き戻し
7. アプリを **再起動** (新しい DB 接続をクリーンに作り直す最も確実な方法)

復元 UI 操作には **タイプ・トゥ・コンファーム** (data-model.md §9.2) を要求。

### 2.5 Export JSON との役割分離

| 軸 | Export JSON | 本 ADR の DB バックアップ |
|----|------------|------------------------|
| 形式 | 単一 JSON (人間可読、Git diff 可) | SQLite バイナリ (sqlite3 CLI で開ける) |
| 取得頻度 | ユーザー明示実行のみ (低頻度) | 日次 auto + 破壊操作毎 (高頻度) |
| 主目的 | **可搬性** (端末移行 / 共有 / 長期アーカイブ) | **ローカル復旧** (誤削除取消 / 破壊操作の安全網) |
| ペイロード | Eager-on-Read 経由で**最新 payload** に揃う (ADR-0006 §2.5) | 取得時点の DB スナップショット (古い payload も含む) |
| インポート / 復元の扱い | コアの import パスでバージョン互換を解決 (data-model.md §12.4) | 上書き復元 + アプリ再起動 |
| データの欠損リスク | 単発実行ゆえに「最後の編集をエクスポートしないままクラッシュ」リスク有 | 自動・直前取得により欠損リスクを最小化 |

両者は補完する。**どちらか一方への依存ではなく、両方を運用する**ことが推奨される。
ユーザーへの案内文も「定期的にエクスポートで可搬コピーを取り、ローカル復旧は自動バックアップに任せる」と整理する。

## 3. Alternatives Considered

### 3.1 取得方法

| 候補 | 評価 |
|------|-----|
| **SQLite Online Backup API (採用)** | アプリ稼働中に取得可能 / WAL 含めた整合性のある状態を取得 / 別の SQLite クライアントで直接開ける |
| ファイルコピー (`cp data.sqlite ...`) | ❌ WAL モード下では `data.sqlite` 単独に未チェックポイント分が含まれない可能性。整合性を欠いた状態でコピーされうる (data-model.md §2) |
| `VACUUM INTO 'backup.sqlite'` | ✅ 整合性は保たれる。✅ 圧縮効果あり。❌ DB ロック時間が長くなる傾向で、large DB ではアプリの書き込みが詰まる。Online Backup API はページ単位で進めるためロック時間を短く保てる |
| `.dump` SQL コマンドベース | ❌ 大量データで遅い / バイナリ BLOB を持ち得ない / 復元時に SQL 実行が必要で手順が増える |
| 外部バックアップツール (restic / borg 等) | ❌ ファイル単位のスナップショット。WAL の問題は同じ。個人ツールに対して過剰。依存追加 |

→ **SQLite Online Backup API 採用**。WAL 整合性 + 取得中も読み書き可能 + 別ツール互換性の三拍子で他案を上回る。

### 3.2 データ変更検知

| 候補 | 評価 |
|------|-----|
| **`data_revision` カウンタ (採用)** | StorageService のコミット単位で +1。「ユーザー編集が無い日は取らない」が単純に表現できる |
| ファイル mtime 比較 | ❌ アプリが起動しただけでも mtime が変わる場合がある (WAL の touch 等)。意味論が安定しない |
| ファイルサイズ + mtime | ❌ 同上。「変化したか」の判定は確実だが「ユーザー編集か」の意味論を持たない |
| 起動毎に取得 (条件なし) | ❌ ストレージを無駄遣い。Eager-on-Read で実は中身が変わっていない日でもバックアップが増える |
| ハッシュ比較 | ❌ DB 全体のハッシュ計算は重い。価値に見合わない |

→ **`data_revision` カウンタ採用**。ユーザー意味論的な「変化があった」を明示的に表現できる唯一の選択肢。

### 3.3 バックアップ種別

| 候補 | 評価 |
|------|-----|
| **3 種類 (auto / pre-op / manual) (採用)** | 自動取得・操作直前安全網・ユーザー意図保存の 3 用途を分離。それぞれローテーション戦略が違うため別ディレクトリで管理 |
| 1 種類 (manual のみ) | ❌ ユーザーが取り忘れる。「Phase 1 ではバックアップ機構あり」(Q-18) を満たさない |
| 1 種類 (auto のみ) | ❌ 破壊的操作直前の確実なバックアップが取れない |
| 2 種類 (auto + manual) | △ pre-op が auto に紛れると「いつ取られたか」がパッと分からず、復旧時に混乱する |

→ **3 種類採用**。

### 3.4 形式 (Export JSON との関係)

| 候補 | 評価 |
|------|-----|
| **DB バックアップは SQLite バイナリ / Export JSON は別運用 (採用)** | 役割が違うものは形式も違う方が分かりやすい。両方持つ |
| DB バックアップも JSON 化 | ❌ 大量行になると JSON が肥大。バックアップは読みやすさよりも復元の高速性が重要 |
| バックアップを廃止し Export JSON のみ | ❌ ユーザーが取り忘れる頻度高。破壊操作の直前自動取得ができない |
| バックアップ + Export を統一形式に | ❌ 互いの目的が違う (可搬 vs 復旧速度) ため一方を犠牲にする |

→ **役割分離採用**。

### 3.5 ローテーション

| 戦略 | 評価 |
|-----|-----|
| **件数ベース (auto: 10 / pre-op: 30 / manual: 無制限) (採用)** | シンプル / 個人ツールで十分予測可能 |
| 期間ベース (例: 30 日経過したら削除) | △ 件数ベースより複雑。個人ツール規模で意義が小さい |
| 容量ベース (例: 合計 1GB を超えたら最古を削除) | ❌ ファイルサイズが行数によって変わるため予測不可。安心感が下がる |
| GFS (祖父・親・子) | ❌ エンタープライズ寄り。個人ツールには過剰 |

→ **件数ベース採用**。

## 4. Consequences

### 4.1 Positive
- **WAL モード下でも整合性のあるバックアップが取れる** (Online Backup API)
- **無駄なバックアップを取らない** (`data_revision` 比較で「変化が無い日は何もしない」)
- **破壊的操作の直前バックアップで復旧可能** (project 削除・import・migration・restore・rebuild_search_index 全てに対応)
- **役割分離が明確** (Export JSON = 可搬 / DB バックアップ = ローカル復旧) でユーザーへの説明もシンプル
- バックアップファイルが SQLite 標準形式なので、外部ツール (`sqlite3`, DB Browser for SQLite 等) で直接覗ける → デバッグ・調査が容易

### 4.2 Negative / Risks
- **ストレージ容量が無制限ではない** — auto 10 + pre-op 30 + manual 無制限 = ファイル件数が累積する。bulk な手動バックアップを残し続けるとディスク圧迫が起こり得る
  - 対策: 設定画面に各カテゴリの占有容量を表示。manual のみユーザーが手動削除する規約 (data-model.md §13.5)
- **バックアップ取得失敗時の挙動** — pre-op で取得失敗したら破壊的操作を中止 (data-model.md §13.4) するが、auto / manual で失敗した場合の通知 UX は要設計
  - 対策: 失敗時はトーストでユーザーに通知 + ログに残す。再試行は次回起動時に自然に行われる (data_revision がまだ ≠ last_backup_revision なため)
- **リストア中のクラッシュ** — 復元プロセスの途中 (`-wal` 削除 → ファイル上書き → 再起動) で異常終了したら DB が破損する可能性
  - 対策: 復元前に `pre-restore` バックアップを取り、復元失敗時にユーザーが手動で復帰できる導線を提供 (data-model.md §13.6)
- **複数端末で同じ `<userdata>/backups/` を共有してはいけない** — クラウド同期 (Dropbox 等) で `<userdata>/` を同期する運用は想定外。同期競合で壊れる
  - 対策: 利用ガイドに「ユーザーデータディレクトリをクラウド同期サービス上に置かない」を明記する (Phase 1 では README 等の文書化のみ)
- **取得頻度が高すぎる懸念** — auto 10 + pre-op 30 で、頻繁に破壊的操作するユーザーは pre-op が多発する。ユーザー操作 1 つに対し pre-op が 1 つ作られるため
  - 対策: pre-op の最新 30 件で十分実用範囲。バルク削除のような UI を将来追加する際は単一バックアップにまとめる検討余地あり

### 4.3 Neutral
- バックアップは SQLite ファイルのため、ストレージ容量は items の量にほぼ比例。trigram インデックス込み (data-model.md §8) でも個人ツール規模では問題にならない
- 取得時間は通常数百 ms〜数秒。アプリの体感に大きく影響しない
- リストア後の再起動は data-model.md §13.6 の必須手順。ユーザーに違和感はあるが安全性のために許容

## 5. Mitigations

| リスク | 対策 |
|-------|------|
| ディスク容量圧迫 | 設定画面に各カテゴリの占有容量を表示。auto / pre-op は件数ローテーション。manual はユーザー削除 |
| auto / manual バックアップの取得失敗 | エラートースト + ログ記録。次回起動で自動再試行 (data_revision 不一致のため) |
| pre-op バックアップ取得失敗 | 紐づく破壊的操作を**中止** (バックアップ無しで破壊的操作はしない、data-model.md §13.4) |
| リストア中のクラッシュ | pre-restore バックアップが残っているため、ユーザーは別ファイルからやり直せる |
| クラウド同期との衝突 | README / 利用ガイドに明記。Phase 1 では文書化のみ。クラウド同期検出機能は持たない |
| `data_revision` の枯渇 (整数オーバーフロー) | `i64` (SQLite INTEGER と整合) で個人ツール規模では実質無限 (約 9.2 × 10^18 まで枯渇しない) |
| バックアップファイル自体の破損 (ストレージエラー) | §2.4.1 のとおり、リストア前に `PRAGMA integrity_check` を 1 度実行 (UI に進行中表示)。失敗時はリストアを中止し、別のバックアップファイル選択を促す |

## 6. Validation Criteria

Phase 1 終了時点で以下を確認する:

- auto / pre-op / manual の 3 種類すべてが想定通り取得され、適切なディレクトリに保存されること
- `data_revision == last_backup_revision` の状態で起動した場合、auto バックアップが**取得されない**こと (data-model.md T-12)
- 24 時間経過しないうちは、`data_revision` が増えても auto は取得されないこと (起動時 1 回ルール)
- 5 つの破壊的操作 (project 削除 / import / migration / restore / rebuild_search_index) すべての直前で pre-op バックアップが取得されること (data-model.md T-13 / T-28)
- pre-op 取得失敗時、紐づく破壊操作が中止されること (data-model.md T-14)
- restore 実行: `-wal` / `-shm` がクリーンに片付き、アプリ再起動が促されること (data-model.md T-15 / T-22)
- バックアップファイルが別の SQLite クライアント (`sqlite3` CLI 等) で開けること
- ローテーション (auto 11 件目で最古削除 / pre-op 31 件目で最古削除 / manual は削除されない) が機能すること

## 7. Known Concerns / 将来見直しが要りうる判断

#### 7.1 ストレージ容量の上限ベースの管理

- 現在は件数ベースのローテーション。将来「合計容量 N GB を超えたら古いものから削除」を追加する選択肢
- **対応**: ユーザーから「PC のディスクが圧迫された」報告が出た時点で検討。Phase 1 では件数で十分

#### 7.2 バックアップ整合性検証 UI

- 現在: リストア前に `PRAGMA integrity_check` を 1 度走らせる程度を Mitigations に書いた
- **将来**: ユーザーが任意のバックアップファイルを「整合性確認」できる UI を提供できると安心感が増す
- **対応**: Phase 1 ではエッジケース。Phase 2 以降で UI 追加検討

#### 7.3 差分バックアップ / 圧縮

- 現在は毎回フルバックアップ。`VACUUM INTO` の圧縮版相当の効果が期待できる代替もある
- **懸念**: ストレージ効率が悪い (毎回フル)
- **対応**: SQLite には差分バックアップの公式機構が無い。差分は外部ツール領域。Phase 1 で導入するメリットは薄い

#### 7.4 クラウドバックアップへの将来展開

- ユーザーから「クラウドにもバックアップしたい」要望が来る可能性
- **懸念**: 現在の設計はローカルファイルシステム前提
- **対応**: 顕在化したら新 ADR で対応。クラウドストレージ API (S3 互換 / Google Drive 等) を経由する形式が基本線。Phase 1 のローカル戦略はそのまま維持し、クラウド側は「追加レイヤ」として乗せる設計を検討

#### 7.5 メタデータ付きバックアップ (ラベル / メモ)

- 現在: ファイル名に prefix / 時刻 / リビジョンしか入らない
- **要望候補**: ユーザーが「重要な編集の前に取った」のような注記を残したい
- **対応**: manual バックアップでのみ「ラベル付き」を許可する案がある (例: `manual-<label>-<timestamp>.sqlite`)。Phase 1 では対象外、Phase 2 で検討
