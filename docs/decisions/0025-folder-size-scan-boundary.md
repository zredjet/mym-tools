# ADR-0025: フォルダ容量の走査の境界

- **Status**: Accepted
- **Date**: 2026-10-17
- **Related**: requirements §2.2 / architecture §10.9 / module-contract §12.15 / ADR-0009 / ADR-0018

## Context

ディスクの空きが減った時に、指定したフォルダの中で何が容量を使っているかを突き止めたい。
OS 標準の Finder / エクスプローラーはフォルダの合計サイズを一覧で並べられず、`du` は結果を
たどりにくい。これまでのモジュールは利用者が選んだファイルか、フォルダ直下だけを読んでおり
(pngopt)、フォルダを再帰的にたどる処理はアプリに無い。

再帰的な走査には、ファイルを 1 つずつ読む処理とは別の問題がある。

- シンボリックリンク・ジャンクション・別のボリュームを辿ると、同じものを重複して数えたり、
  ループしたり、意図しないネットワーク上の場所に触れたりする。
- Windows ではネットワーク上のパスに触れた時点で SMB 接続が走り、サインイン情報 (NTLM 認証) が
  サーバへ送られる (M-Link と同じ問題、data-model §10.2)。
- ファイルの「大きさ」と「ディスク上で使っている領域」は、圧縮・スパース・クラウド上だけにある
  ファイル・小さなファイルの多さで大きく違う。容量の原因を探すには両方が要る。
- 権限で読めないフォルダがある。Windows では管理者だけが読めるフォルダが多く、macOS では
  プライバシー保護 (TCC) で読めないフォルダがある。
- 数百万のファイルを含むフォルダもあり、全件を IPC で返すことはできない。

## Decision

- `dirsize` (表示名「フォルダ容量」) を `category = other`、`is_stateless = true`、既定有効の
  独立モジュールとする。入力 path・結果は items や settings に保存しない (D-06)。
- **読み取り専用**とする。削除・移動・ごみ箱への移動は作らない (requirements §4.1「ファイル管理
  ツールにはしない」)。結果の行からは Finder / エクスプローラーで表示 (`opener:default` に含まれる
  `reveal_item_in_dir`) とパスのコピーだけを行う。
- 走査は Rust の固有コマンド `dirsize_scan` で行う。Frontend は path だけを渡す。
- **ローカルのフォルダだけ**を対象にする。ルートは次の順に確かめ、ファイルシステムに触る前に
  文字列で分かるものを拒否する。
  1. 空・相対パスを拒否する
  2. UNC や device path (`\\server\share`、`//server/share`、`\\?\UNC\...`、`\??\...`) を拒否する。
     判定は M-Link と共通の `modules/network_path.rs` (`pub(crate)`) に置く
  3. Windows はドライブ文字のパスの `GetDriveTypeW` が `DRIVE_REMOTE` なら拒否する
     (割り当てたネットワークドライブ)。macOS は `statfs` の `MNT_LOCAL` が無ければ拒否する
     (`/Volumes` 配下の SMB など)。`libc` を macOS 向けの直接の依存にする (既に間接依存している版)
  4. `fs::metadata` でフォルダであることを確かめる (ルートだけはリンクを辿る)
- 走査は `tauri::async_runtime::spawn_blocking` の単一スレッドで、明示スタックの深さ優先で行う。
  `walkdir` / `jwalk` は使わない (jwalk は rayon を使い ADR-0009 R-2 に反する。walkdir は
  取消しの確認と読めないフォルダの扱いを自分で書くのと手間が変わらない)。
  - シンボリックリンクと、Windows のジャンクション・マウントポイント (std の `is_symlink` が
    name surrogate の reparse point を含む) は辿らず、件数だけ数える。
  - macOS / Linux はルートと `st_dev` が違うフォルダ (別のボリューム) に入らない。
  - 隠しファイル・隠しフォルダも数える (`.git` などが原因になりうるため)。
  - 項目ごとに `CancellationToken` を確かめ、取消し時は結果を返さない。進捗は Channel で
    100 ms ごとに送る (ファイル数・フォルダ数・合計・いま読んでいるフォルダ)。
- 大きさは 2 種類を集計する。
  - 「サイズ」: `metadata.len()` (ファイル内容のバイト数)。
  - 「ディスク上」: macOS / Linux は `st_blocks × 512`。Windows は属性が圧縮・スパース・
    オフライン・クラウド上だけ (RECALL_ON_*) のファイルだけ `GetCompressedFileSizeW` で問い合わせ、
    それ以外は `len` をクラスタの大きさへ切り上げる。失敗時は `len` を使う。
  - Windows の大きさと属性は親フォルダの一覧 (FindNextFile) から取り、ファイル自体は開かない。
    親が読めれば `pagefile.sys` のような開けないファイルも数えられる。
  - フォルダ自身の領域は数えない。
  - macOS / Linux のハードリンクは `(st_dev, st_ino)` で 2 回目以降を数えない (`du` と同じ)。
- 読めないフォルダは「読めない」印を付けて走査を続ける。件数と先頭 100 件のパスを返し、ルートが
  読めない時だけエラーにする。**管理者権限への昇格や権限の回避はしない。** 代わりに次を出す。
  - Windows でドライブ直下を走査した時は、`GetDiskFreeSpaceExW` の使用量と集計した「ディスク上」の
    差を「見えなかった容量」として出す。macOS は APFS のボリュームがコンテナの空きを共有し、
    差が誤解を生むため出さない。
  - 読めないフォルダの案内を OS ごとに出す (Windows は管理者権限、macOS はフルディスクアクセス)。
    `System Volume Information`・`$Recycle.Bin`・`WindowsApps` には何のフォルダかの説明を付ける。
- 返す内容を絞る。フォルダは走査中に全件を持ち、ファイルは大きい順の上位だけを名前付きで残す。
  「サイズ」と「ディスク上」それぞれの上位 10,000 件の和集合 (最大 20,000 件) を返す。
  親は子以上の大きさなので、同じ大きさなら浅い方を先に並べれば祖先は必ず含まれる。
  含めなかった直下の項目は、フォルダごとに件数と大きさ (「ほか n 項目」) にまとめる。
  読めないフォルダは上位に入らなくても先頭 1,000 件を祖先ごと残す (中身が 0 扱いで埋もれるため)。
- 上限はフォルダ 1,000,000 件とし、達したら走査を止めて途中までの集計を返す (画面に明示する)。
  フォルダ 1 件あたり約 100 バイトを持つ。
- パスはルートと名前と区切り文字から Frontend が組み立てる。UTF-8 にできない名前は置換文字で
  表し、そのパスは「表示」に使わない。

## Alternatives Considered

| 候補 | 判断 |
|---|---|
| Rust の単一スレッドで `read_dir` を再帰 | **採用**。依存を足さず、取消し・読めないフォルダ・リンクの扱いを明示できる |
| `jwalk` で並列に走査 | 不採用。rayon を使い ADR-0009 R-2 に反する |
| NTFS の MFT を直接読む (WizTree 方式) | 不採用 (初版)。管理者権限が要り、NTFS の解析を自前で持つことになる |
| 全ノードを Frontend へ返す | 不採用。数百万件で IPC と描画が持たない |
| Rust 側に結果を保持して子を遅延取得 | 不採用 (初版)。stateless のまま一度の応答で済む上位 K 件で、原因を探す用途には足りる |
| 管理者として走査する (UAC で昇格) | 今回は不採用。昇格した別プロセスとの通信路の設計が要るため、別の ADR で扱う |
| ごみ箱への移動・削除 | 不採用。読み取り専用に限る (requirements §4.1) |

## Consequences

- ネットワークも外部ツールも使わずに、フォルダの容量を大きい順にたどれる。「サイズ」と
  「ディスク上」の差から、小さなファイルの多さやクラウド上だけのファイルにも気付ける。
- 結果は最大 20,000 件 (JSON で約 5 MB)。小さな項目は「ほか n 項目」にまとまり、中身はその
  フォルダを走査し直すと見られる。
- 管理者だけが読めるフォルダの中身は数えられない。Windows のドライブ直下では差を出すので、
  どれだけ見えていないかは分かる。
- APFS のクローンは区別できず、重複して数える。Windows のハードリンクはファイルを開かないと
  分からないため、重複して数える。Windows の MFT に収まる小さなファイルも 1 クラスタとして数える。
- 実測 (M4 Max の APFS): 約 21 万ファイル・1.6 万フォルダが約 1 秒、約 120 万ファイル・8 万
  フォルダが約 34 秒。「サイズ」と「ディスク上」は Python の `os.scandir` + `lstat` と一致し、
  「ディスク上」は `du -sk` と一致した。

## Validation Criteria

- フォルダごとの合計、ファイル数・フォルダ数が正しい。リンクを辿らず、ハードリンクを 1 回だけ
  数える。読めないフォルダを報告し、上位に入らなくても祖先ごとツリーに残る。
- 上位 K 件の絞り込みで、すべてのノードの親が結果に含まれる (同じ大きさが入れ子になる場合を含む)。
  同じ大きさのファイルが大量にあっても候補が増え続けない。
- 開始前・走査中の取消し、フォルダ数の上限、空・相対パス・UNC・ファイル・存在しないパスの拒否。
- macOS 実機で、リポジトリや `~/Library` の結果を `du -sk` と照合する。`/Volumes` の SMB
  マウントを拒否する。
- Windows 実機で、`C:\` 直下の読めないフォルダの表示と「見えなかった容量」、`pagefile.sys` を
  数えられること、OneDrive の未ダウンロードのファイルで「ディスク上」が小さくなること、
  割り当てたネットワークドライブと UNC の拒否、長いパスを確かめる。
